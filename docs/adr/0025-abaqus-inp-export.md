# ADR 0025. Экспорт Abaqus `.inp`: чтение модели через C ABI, раскладка файла, возврат passthrough

- Статус: принято
- Дата: 2026-10-18
- Источник: задача 3.3 из `docs/plan.md`; `docs/architecture.md` §3 (Passthrough), §4.6 п. 6 (`describe_losses`), §7;
  ADR 0024 «Последствия» (экспорт возвращает `abaqus_keyword` на места; нужно чтение больших данных через C ABI);
  пункты бэклога «Большие данные через C ABI», «Элементы неподдержанных типов и наборы»
- Код: `core/include/fem/extension_abi.h` (`read_model`, `object_data`), `core/src/extension/native_runtime.cpp`;
  `extensions/fem.format.abaqus-inp/src/inp/model.h`, `export.{h,cpp}`, `numbers.cpp` (`format_number`),
  `import.cpp` (места в файле), `src/module.cpp` (`inp.export`, `inp.describe_losses`), манифест, схемы, переводы;
  справочник `docs/extensions/fem.format.abaqus-inp.md`

## Контекст

Импорт (3.2) кладёт в модель сетки, наборы и объекты `fem.model.structural`, а непонятое — объектами `abaqus_keyword`
с файлом, строкой и номером ключевого слова. Экспорт должен записать модель обратно так, чтобы «открыл и сохранил без
изменений» давало ту же модель по смыслу, а `describe_losses(model)` заранее называл, чего файл не удержит. Нативный
модуль мог только создавать объекты (`create_object`), но не читать модель.

## Решения

1. **Чтение модели через C ABI.** `FemCommandApi` дополнен в конце (версия ABI осталась 1, модули проверяют
   `struct_size`): `read_model(call)` — JSON модели без больших данных (единицы; объекты в порядке дерева с типом,
   владельцем, именем, родителем, зависимостями, свойствами, видом данных и признаком непрозрачности);
   `object_data(call, id, &data)` — массивы сетки и наборов **без копирования**: указатели в неизменяемые `Mesh`,
   `NodeSet`, `ElementSet`, действительные до конца вызова (вызов держит `shared_ptr` на данные). Поверхность
   копируется в пары `int32_t`: раскладка `ElementSide` не входит в ABI. `ArrayData` даёт `FEM_DATA_NONE` (вид
   добавит чтение `.frd`, 3.6).

2. **Писатель без ядра.** `fem_inp_reader` получил `export_model(Model, file_stem)`: `Model` — объекты с видами
   (`std::span`) на данные; модуль строит его из `read_model`/`object_data`, тесты — из результата импорта
   (`model_of`). Тот же код без текста — `describe_losses`, поэтому список потерь всегда совпадает с тем, что
   делает экспорт. Числа — кратчайшая запись, которая читается обратно в то же `double`, без учёта локали
   (`std::to_chars`, иначе `%.15g`…`%.17g` с проверкой). Выход детерминирован: та же модель — те же байты.

3. **Раскладка файла.** Одна сетка без деталей — плоский файл (как пишет CalculiX). Иначе каждая сетка — `*PART` и
   `*INSTANCE` без переноса и поворота (координаты в модели уже в системе сборки, метки — как в файле), узлы самой
   сборки — в `*ASSEMBLY`. Порядок: `*HEADING`, детали (узлы, элементы по блокам с типом Abaqus из
   `abaqus_element_types`, наборы детали, сечения), сборка (инстансы, наборы сборки с `INSTANCE=`, поверхности
   с `инстанс.метка`), ключевые слова модели из passthrough, материалы, ГУ модели, шаги. Сетке без
   `abaqus_element_types` (мешер) тип даётся по форме (tet10 → C3D10…). Ссылки из истории — `инстанс.набор` для
   наборов детали и имя для наборов сборки; набор сборки, переименованный импортом в `<сборка>.<имя>`, получает
   имя обратно.

4. **Импорт запоминает места для экспорта** (новые необязательные свойства, схемы остались версии 1):
   `abaqus_input.steps` — имена всех шагов в порядке файла (шаги не `*STATIC` хранятся целиком в passthrough и
   встают между остальными), `abaqus_input.assembly`; `abaqus_element_types.part`, `instance`, `assembly`,
   `partSets` (какие наборы сетки — наборы детали), `keptMembers` (метки наборов, которых нет в сетке: элементы
   типов, ушедших в passthrough, — экспорт возвращает их в `*ELSET`, решение пункта бэклога);
   `abaqus_keyword.position` — сколько объектов шага идёт перед ключевым словом. Версия схемы не повышена: старые
   объекты без этих свойств читаются и экспортируются с умолчаниями (порядок шагов — порядок дерева, все наборы —
   наборы детали). Отклонение от плана задачи: там предлагалась версия 2 с миграцией — она не нужна, раз все
   свойства необязательны.

5. **Возврат passthrough.** Ключевое слово возвращается в своё место: в шаг — по `position` среди объектов шага,
   в материал — после `*ELASTIC`/`*DENSITY`, в инстанс, деталь (первую из её инстансов), сборку или в данные модели
   (перед материалами, чтобы не стать подопцией материала) — по `index`. Ключевое слово, чьего места больше нет
   (удалена деталь), не пишется и попадает в потери.

6. **«Тот же смысл» — проверяемое определение.** Тест сравнивает отпечатки модели до и после «экспорт → импорт»:
   сетки по меткам (координаты точно), типы Abaqus, наборы как множества меток, места сеток, материалы, сечения и
   нагрузки со свойствами и целями, шаги с объектами и passthrough по местам, порядок шагов, passthrough по местам
   в порядке файла. Не сравниваются id, файлы и строки passthrough и имена, которых нет в синтаксисе `.inp`
   (сечения, ГУ, нагрузки, запросы вывода импорт называет по целям). Второй экспорт файла даёт те же байты.

7. **Потери (`describe_losses`) — проблемы `loss.*`** с аргументами, переводятся каталогами модуля: единиц в
   `.inp` нет (всегда, `info`); инстансы одной детали становятся отдельными деталями; сетка плоского файла получит
   имя файла; тип элемента без аналога Abaqus (пирамиды); интегрирование сечения, не совпадающее с типами
   элементов; нагрузка или вывод вне шага; объект без цели; объект на нескольких целях станет несколькими;
   стороны поверхности не на гранях объёмных элементов; объекты других модулей и результаты; passthrough без
   места. Команда `inp.export` сообщает их во вкладку «Проблемы», `inp.describe_losses(path=…)` возвращает
   списком (`message`, `args`, `severity`, английский `text`) без записи файла.

8. **Команды.** `inp.export(path)` пишет файл через временный `<файл>.part` и переименование (сбой записи не портит
   старый файл), журналируется, модель не меняет (шага undo нет), возвращает число ключевых слов. Формат
   `abaqus-inp-export` роли `model-export`. Пункт «Файл → Экспорт…» в оболочке не сделан (бэклог).

## Рассмотренные альтернативы

- **Копировать сетку в JSON или в буфер модуля** — проще ABI, но удваивает память на миллионах элементов.
  Отклонено: данные модели неизменяемы, указателей до конца вызова достаточно.
- **Восстанавливать общую деталь с преобразованием инстанса** (поиск поворота и переноса по узлам) — точнее
  повторяет исходный файл, но хрупко и не нужно решателю. Отклонено: потеря названа.
- **Хранить порядок всех ключевых слов файла** в одном списке объекта файла — точный порядок, но любое изменение
  модели ломает список. Отклонено в пользу мест по областям (`position`, `index`, `steps`).
- **Детали всегда, даже для одной сетки** — единообразно, но CalculiX не читает `*PART`/`*ASSEMBLY`. Отклонено.

## Последствия

- Адаптер CalculiX (3.5) пишет вход тем же писателем (плоский файл при одной сетке) и добавляет проверки
  `validate()` к потерям; несколько сеток для CalculiX придётся сводить в одну с перенумерацией.
- Чтение `.frd` (3.6) добавит вид `ArrayData` в `object_data`.
- «Файл → Экспорт…» и диалог потерь перед записью — с открытием `.inp` новым документом (3.10) или раньше по запросу.
