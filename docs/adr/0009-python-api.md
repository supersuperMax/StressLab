# ADR 0009. Python API: nanobind, встроенный интерпретатор, обёртки команд

- Статус: принято
- Дата: 2026-10-13
- Источник: `docs/architecture.md` §4.6 (п. 5, 7), §4.7, задача 1.8 из `docs/plan.md`
- Код: `python/bindings/` (`fem::python`, нативный модуль `_stresslab`), `python/embed/`
  (`fem::python::Interpreter`), `python/stresslab/` (пакет `stresslab`), `app/main.cpp` (`stresslab --python`)

## Контекст

С задачи 1.3 журнал сессии `.slpy` — скрипт Python (`stresslab.cmd(...)`, `undo`, `redo`,
`with stresslab.transaction(...)`), но исполнял его только внутренний парсер-заглушка ядра. Нужен настоящий
модуль `stresslab`: документ и объекты, команды и типизированные обёртки, массивы сетки как numpy без копий,
context keys и Task, причём один и тот же код должен работать и в обычном `python`, и во встроенном в
приложение интерпретаторе (там скрипты меняют документ приложения). При этом правила 3 (модель меняется
только командами) и 7 (долгие операции — Task) должны действовать и для кода на Python.

## Решения

1. **Две части пакета.** Нативный модуль `_stresslab` (nanobind) и чистый пакет `stresslab` поверх него
   (функции уровня модуля, обёртки команд, `run_task`). Привязки — статическая библиотека
   `fem_python_bindings`; из неё собираются модуль расширения для обычного Python
   (`build/<пресет>/python/site/_stresslab*.pyd|so`, рядом — копия пакета и на Windows нужные DLL) и
   встроенный модуль исполняемых файлов (`PyImport_AppendInittab`). Встроенный модуль находится раньше файла
   расширения (`BuiltinImporter` стоит перед `PathFinder`), поэтому внутри приложения Python работает с ядром
   приложения, а не со второй копией.
2. **nanobind из pip, а не из vcpkg.** Порт vcpkg `nanobind` зависит от порта `python3` и собирает свой
   CPython, на котором нет numpy и pytest; встраивать же нужно тот Python, на котором идут тесты и стоят пакеты
   пользователя. nanobind 2.13.0 закреплён в `python/requirements-dev.txt`, CMake находит его через
   `python -m nanobind --cmake_dir`. Python 3.12 ищет корневой `CMakeLists.txt` (`FindPython 3.12 EXACT`,
   `Development.Module` и `Development.Embed`); в CI его даёт `setup-python` (`Python_ROOT_DIR`).
3. **Документ — ручка.** `stresslab.Document` держит `DocumentHandle`: либо документ с шиной, созданный в
   Python (живёт, пока на него есть ссылки), либо документ приложения, одолженный через
   `Session::attach(bus, keys)` и возвращаемый `detach`. После `detach` любое обращение — `ClosedError`, а не
   доступ к освобождённой памяти. **Активный документ** — тот, что меняет `stresslab.cmd` (и что пишет
   журнал): внутри приложения — документ приложения, в обычном процессе — новый документ при первом
   обращении; `set_active_document`/`new_document` меняют его.
4. **Объекты — представления `(документ, id)`**: каждое чтение идёт в модель, удалённый объект даёт
   `ModelError(unknown_object)`, `properties` — копия. Менять модель можно только командами; код команды на
   Python получает `CommandContext` (`execute` — подкоманда в том же шаге, `create_object`, `set_data` —
   через `DocumentEditor` шины), так что undo и откат при исключении работают как у команд на C++.
   Включить объекты модуля (`set_owner_enabled`) можно только в документе, созданном в Python: в документе
   приложения это делает Extension Manager.
5. **Значения.** Python → `Value`: `None`, `bool`, `int` (в пределах int64), `float`, `str` (UTF-8, одиночные
   суррогаты — `UnicodeEncodeError`), `os.PathLike` → путь, `list`/`tuple` → список, `dict` с ключами `str`,
   `stresslab.Object` → его id, целые numpy через `__index__`. Остальное — `TypeError`; NaN и бесконечности
   отвергает шина (`CommandError(invalid_value)`). Пути возвращаются как `pathlib.Path`.
6. **`cmd` возвращает** значение команды или `Task`, если команда ушла в фон (`CommandResult::task`).
7. **Типизированные обёртки строятся из реестра при обращении**: PEP 562 `__getattr__` пакета
   (`stresslab.model.create`), `stresslab.commands` (активный документ), `Document.commands` (данный
   документ). Это функции с настоящим `inspect.Signature`: только именованные параметры в порядке спецификации,
   аннотации по `ArgType`, у необязательных — значение по умолчанию или `None`. Аргументы проверяются
   `Signature.bind` до шины, в шину уходят только переданные (умолчания в журнал не попадают). Вызов обёртки —
   это `cmd(id, ...)`, и журнал всегда пишет `stresslab.cmd(...)`.
   **Имена** (пункт бэклога из 1.3): в каждом сегменте id `-` заменяется на `_`, ключевое слово Python
   получает суффикс `_` (`fem.format.ansys-cdb.import` → `stresslab.fem.format.ansys_cdb.import_`). Если два
   id дают один путь, обёртка отвергается (`AttributeError`, «ambiguous»), команды запускаются через `cmd`.
   Имена самого пакета (`context`, `cmd`, …) скрывают одноимённые сегменты, те доступны через
   `stresslab.commands`.
8. **Массивы сетки без копий.** `Mesh`, `ElementBlock`, `NodeSet`, `ElementSet`, `Surface` отдают numpy-массивы
   поверх данных ядра: nanobind делает `numpy.asarray` над своим объектом с протоколом буфера, помеченным
   «только чтение». Данные ядра неизменяемы и разделяются через `shared_ptr`; капсула массива держит его,
   поэтому массив переживает объект и документ, а undo/redo возвращает те же адреса. Флаг `writeable` включить
   нельзя — модель не меняется в обход шины. `connectivity` — `(n, узлов на элемент)` `int32`, поверхность —
   `(n, 2)`. Входные массивы (новая сетка в команде на Python) копируются в векторы ядра с проверкой: дробные в
   целые — `TypeError`, выход за `int32` — `ValueError`.
9. **Context keys** — `stresslab.context`: чтение, `set`/`update` (пакетно), `declare`, `remove_owner`,
   `evaluate`, `watch`. В обычном процессе у сессии свои ключи, а ключи ядра (`CoreKeys`) следуют за активным
   документом; встроенный интерпретатор работает с ключами приложения.
10. **Task**: состояние, прогресс, сообщения, `cancel`, `wait`/`result` с таймаутом без GIL, `subscribe`.
    `make_task` даёт пару (Task, TaskControl), `stresslab.run_task(title, work)` выполняет работу в своём
    потоке; команда на Python может вернуть Task. Методы, которые оповещают слушателей, отпускают GIL:
    слушатель в рабочем потоке держит замок слота, пока ждёт GIL.
11. **Что Python держит в ядре** (слушатели, код команд, открытые транзакции) учитывается (`PythonResource`) и
    освобождается при `detach` и в `atexit`-хуке модуля, пока Python ещё жив. Хук закрывает и все документы,
    созданные в Python: слушатель может ссылаться на объект, который держит документ, — цикл через C++,
    невидимый сборщику мусора. Подписка (`Subscription`) живёт до `close()` (или закрытия документа), а не до
    удаления объекта Python — как `connect` в обычных системах событий. Исключение слушателя печатается как
    «unraisable» и не ломает команду или изменение ключей; исключение кода команды откатывает команду и
    доходит до вызывающего. Объекты Python, которые C++ отпускает на других потоках, отпускаются под GIL.
12. **Ошибки ядра** — исключения `stresslab.*Error` (наследники `stresslab.Error` ← `RuntimeError`) с полем
    `code` из `to_string(code)`; у `WhenSyntaxError` ещё `column` и `reason`.
13. **Встроенный интерпретатор** (`fem::python::Interpreter`): CPython 3.12 в режиме UTF-8 на всех ОС;
    стандартная библиотека — от Python сборки (`home` = его `sys.base_prefix`, если не задан `PYTHONHOME`),
    его site-packages (и виртуального окружения) добавляются через `site.addsitedir`, пакет `stresslab` — из
    папки сборки. `run_file`/`run_string` превращают исключение в `PythonError` с traceback, `SystemExit(0)` —
    успех. `stresslab --python [аргументы]` запускает Python как команду `python` (`Py_RunMain`) с документом и
    ключами приложения: так идут `stresslab --python -m pytest` и журналы. Python, поставляемый с программой, —
    задача 3.11. Предупреждения nanobind об «утечках» при выходе включены в Debug и выключены в Release.
14. **Парсер журнала в ядре остаётся.** Он не нужен Python, но ядро и C++-тесты воспроизводят журнал без
    интерпретатора; C++-тест сверяет оба пути (`tests/unit/python/journal_script_test.cpp`).

## Рассмотренные альтернативы

- **pybind11** (запасной вариант из §4.7) — больше и медленнее компилируется; nanobind даёт `ndarray` с
  экспортом в numpy и поддерживает встраивание через `NB_MODULE` + inittab.
- **Порт vcpkg `nanobind`** — см. п. 2: второй CPython без пакетов пользователя.
- **Обёртки команд, сгенерированные в файл при сборке** — устаревали бы при включении модулей; динамические
  обёртки следуют за реестром. Файлы `.pyi` для подсказок IDE — в бэклоге (этап 8).
- **Свой объект с протоколом буфера вместо `nanobind::ndarray`** — то же самое руками; nanobind уже помечает
  массив «только чтение» и держит владельца капсулой.
- **Подписка, которая отключается при удалении объекта Python** (RAII, как в C++) — молча теряла бы
  слушателей, результат `doc.on_journal(print)` без присваивания не работал бы.
- **`PyConfig.executable` вместо `home`** — на Windows getpath ищет stdlib от `python312.dll` рядом с
  программой, а не от `executable`, и не находит её.

## Последствия

- Задача 1.9 (extension host) переиспользует `stresslab` в процессе хоста; команды модулей на Python будут
  регистрироваться через JSON-RPC, а `register_command` в процессе приложения остаётся для быстрых скриптов
  (§4.4) и тестов.
- `--headless run-script` (1.10) строится на `Interpreter` (attach документа, `run_file`, код возврата).
- Настройки, локализация, Job Manager и Extension Manager в Python пока не выведены (ADR 0008 обещал
  настройки и переводы к 1.8, но задача их не называет): в бэклоге вместе с вопросом о журналировании
  настроек.
- C++-тесты, встраивающие Python, не могут запустить его дважды: один интерпретатор на процесс
  (`::testing::Environment`).
