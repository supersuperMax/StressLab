# ADR 0016. Демонстрационный модуль, `stresslab.extensions` и включение модулей в журнале

- Статус: принято
- Дата: 2026-10-15
- Источник: задача 1.15 из `docs/plan.md` (приёмка этапа 1); `docs/architecture.md` §4.2, §4.6 пп. 2, 4, 5,
  §4.7; пункты бэклога «Включение модулей в журнале» и «Изменения настроек в журнале и настройки в Python»
- Код: `extensions/fem.demo/`, `core/include/fem/core/command/command_bus.h` (`journal_action`),
  `core/include/fem/core/extension/manager.h` (`Journaling`, `SettingReader`), `runtime.h`
  (`ExtensionHost::setting`), `core/src/extension/host_runtime.cpp` (`settings/get`), `core/src/bindings.cpp`,
  `python/bindings/src/extensions.cpp`, `python/stresslab/extensions.py`, `python/stresslab_host/_host.py`
  (`setting`), `python/embed` (`Interpreter::attach`), `shell/src/` (`extensions_panel.cpp`,
  `command_palette.cpp`, `required_modules_bar.cpp`, `contribution_ui.cpp`, `main_window.cpp`),
  `docs/extension-guide.md`

## Контекст

Приёмка этапа 1: демонстрационный модуль добавляет кнопку, команду, вкладку, этап, узел с формой и
настройку; при выключении они исчезают, при включении возвращаются; то же из консоли Python и из `--headless`.
Для этого не хватало трёх вещей:

- из Python нельзя было включить или выключить модуль: интерпретатор знал только документ и ключи;
- включение модулей не попадало в журнал, поэтому журнал сессии, где пользователь выключил модуль,
  воспроизводился в другом состоянии (бэклог, ADR 0006 «Последствия»);
- код модуля не мог прочитать свою настройку, и настройка в демо-модуле оставалась бы украшением.

## Решения

1. **Включение и выключение — действие сессии, а не команда.** В бэклоге было два вопроса: что делает откат
   транзакции, внутри которой включили модуль, и кто владеет командами менеджера (команды `fem.core` нельзя
   снять с шины). Ответ: это не команда Command Bus и не шаг undo. Новое `CommandBus::journal_action(entry)`
   пишет в журнал строку Python, которая повторяет действие. Шага undo нет, шаги redo остаются. Внутри команды и
   открытой транзакции действие запрещено (`CommandError(invalid_state)`), поэтому откатывать нечего.
   Модель включение не меняет: объекты модуля только становятся непрозрачными или перестают ими быть (ADR 0002).

2. **`Journaling::on` у `ExtensionManager::enable`, `disable`, `apply_profile`.** Журналируется то, что сделал
   пользователь: переключатель и «Включить/Выключить» в менеджере модулей, установка из папки с включением,
   применение профиля, «Включить» в палитре и в полосе нужных модулей, `stresslab.extensions` в Python.
   Включение при старте приложения (`Application`) идёт с `Journaling::off`: оно не действие пользователя, и
   журнал не начинается с длинного списка. Строки:
   - `stresslab.extensions.enable("id")` и `disable("id")` — вызов, как его сделал пользователь (с зависимостями
     разбирается при воспроизведении). Пишется и тогда, когда модуль уже был в этом состоянии: при
     воспроизведении в окне, где пользователь выключил модуль, журнал даст тот же результат;
   - профиль — строками `disable` для каждого модуля из `ProfileReport::disabled`, затем `enable` для
     `ProfileReport::enabled`. Путь к файлу профиля в журнал не пишется: на другой машине его может не быть;
   - если вызов не удался, ничего не пишется. Внутри команды или транзакции вызов отклоняется до изменений
     (`ExtensionError(invalid_state)`).

   `uninstall` и `reload` не журналируются: это установка, а не работа с моделью. Журнал, которому нужен модуль,
   воспроизводится там, где модуль установлен.

3. **`stresslab.extensions` — подмодуль Python поверх менеджера приложения.** `installed()`, `get(id)`
   (`ExtensionInfo` — снимок: `id`, `name` как в манифесте, `version`, `kind`, `source`, `state`, `enabled`,
   `folder`), `enable(id)`, `disable(id)` (возвращают id затронутых модулей, всегда с `Journaling::on`).
   Менеджер одалживается так же, как документ и ключи: `Interpreter::attach(bus, keys, &manager)` в окне и в
   headless. Ошибки менеджера в Python — новый `stresslab.ExtensionError` (наследник `stresslab.Error`, с
   `code`); его же получают команды модулей, упавшие в коде модуля. В обычном Python и в `stresslab --python`
   менеджера нет: вызовы бросают `ExtensionError(invalid_state)` «modules are managed by the application».
   Своего менеджера для документов, созданных в Python, не делали: модулям нужен extension host приложения.
   Журнал со строками `stresslab.extensions.*` воспроизводится в `stresslab --headless run-script` и в консоли
   окна, но не в обычном Python. Внутренний разбор журнала ядра (`parse_journal`, заглушка из 1.3 для тестов)
   этих строк не знает.

4. **Код модуля читает настройки: `settings/get`.** `ExtensionHost::setting(key)` возвращает значение в силе
   (по умолчанию < пользователь < проект) любой настройки со схемой; для ключа без схемы —
   `ExtensionError(unknown_setting)`, по протоколу — ошибка `-32004`. Менеджер не зависит от `settings`:
   `bind_settings` (`fem/core/bindings.h`) даёт ему `SettingReader` и снимает его вместе с подпиской. В
   `stresslab_host` — `Extension.setting(key)` и `Call.setting(key)`. Уведомления об изменении настройки нет:
   модуль читает настройку, когда она нужна (CalculiX прочтёт путь к `ccx` перед запуском).

5. **`stresslab.settings` в Python отложены до задачи 2.1** (решение пользователя). Настройки по-прежнему
   меняются мимо Command Bus (ADR 0008 п. 7). Записывать ли их изменения в журнал и делать ли настройки
   проекта частью модели, удобнее решать вместе с папкой проекта, где они хранятся.

6. **`extensions/fem.demo` — встроенный python-модуль без МКЭ-специфики.** Он хранит в модели заметки
   (`demo_note`, owner `fem.demo`):
   - команда `demo.add_note(text="")`: пустой текст берётся из настройки `demo.defaultText`, имя `#N`;
   - кнопка на контекстной панели с `when = "stage == 'demo.review'"`;
   - этап `demo.review` в слоте `after:results`;
   - вкладка нижней панели `demo.notes`;
   - тип узла `demo_note` с формой: обязательный текст, выбор с `x-enumTitles`, длина с `x-quantity` в
     «Дополнительно»;
   - настройка `demo.defaultText` (`scope = "user"`, по умолчанию `TODO`: значение по умолчанию не переводится);
   - все строки на английском и русском.

   Код активируется первой командой модуля (`onCommand:demo.*`), поэтому, пока модуль не используют, процесс
   хоста не запускается. Как встроенный модуль, он включён по умолчанию. Убрать его из поставки или выключить
   по умолчанию решается в 3.11 (бэклог).

7. **Панели модулей удаляются отложенно (`deleteLater`).** Qt ADS 4.5.0 ставит в очередь вызов с указателем на
   вкладку панели, которую только что сделал текущей (`DockAreaTabBarPrivate::updateTabs` →
   `ensureWidgetVisible`). Если модуль выключить до цикла событий (`enable(...); disable(...)` одной строкой
   консоли, профиль сразу после включения), оболочка удаляла панель сразу, и вызов из очереди обращался к
   освобождённой памяти. Теперь `ContributionUi::remove_panel` снимает панель с `CDockManager` сразу, а удаляет
   её в цикле событий. Ошибку нашёл скриншот-тест fem.demo; регрессионный тест —
   `DemoAcceptance.SwitchingSeveralTimesBeforeTheEventLoopRunsIsSafe`.

8. **Панели модулей, которых нет в восстановленной раскладке, встают на свои места.** Qt ADS делает
   плавающим окном каждую панель, которую не называет восстановленное состояние. Раскладка последней сессии,
   сохранённая до появления модуля (обновление приложения, новый модуль), поэтому выбрасывала вкладку
   модуля плавающим окном посреди экрана. Так случилось с fem.demo при запуске настоящего окна; ошибка есть с
   1.12, но раньше встроенных модулей с вкладками не было. После `restoreState`
   (`MainWindow::restore_layout`) `ContributionUi::dock_panels_missing_from(state)` ставит панели модулей,
   которых нет в XML состояния (`Name="tab:…"`), туда же, куда новые: вкладки — в нижнюю панель позади текущей,
   активности — к дереву, закрытыми. Панель, которую раскладка называет (в том числе плавающую, если её так
   поставил пользователь), остаётся, где была. Тест —
   `DemoAcceptance.ALayoutSavedWithoutTheModuleKeepsItsTabInTheBottomPanel`.

## Рассмотренные альтернативы

- **Включение модуля как команда `fem.core` с undo.** Undo включения означало бы выключение модуля — побочный
  эффект за пределами модели. Кроме того, откат транзакции не может снять зарегистрированные команды и процесс
  хоста. Отклонено (п. 1).
- **Журналировать любое включение, в том числе при старте.** Журнал каждой сессии начинался бы со списка всех
  модулей, а воспроизведение в headless (где включено всё) повторяло бы его впустую. Отклонено (п. 2).
- **Писать в журнал только изменения состояния.** Вызов `enable` уже включённого модуля не попал бы в журнал, и
  журнал не воспроизвёлся бы в окне, где пользователь этот модуль выключил. Отклонено (п. 2).
- **Протокольное уведомление `settings/changed`.** Модулю пришлось бы подписываться и хранить копию настроек.
  Ни одному модулю это пока не нужно — в бэклоге.
- **Тексты по умолчанию для настроек через `%key%`.** Значение по умолчанию — данные, а не подпись: код модуля
  получил бы `%setting…%`. Отклонено (п. 6).
