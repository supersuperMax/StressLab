# ADR 0017. Папка проекта `.slproj`, детерминированный JSON и загрузка модели мимо Command Bus

- Статус: принято
- Дата: 2026-10-15
- Источник: задача 2.1 из `docs/plan.md`; `docs/architecture.md` §3.1 «Как устроено хранение» и «Риски»;
  `docs/interface-design.md` §12 (Ctrl/Cmd+S, автосохранение); пункты бэклога «Загрузка проекта мимо Command
  Bus», «Имена объектов и регистр в файловой системе», «Большие наборы в хранилище проекта», «Round-trip тесты
  сериализации для `mesh`, `node_set`, `element_set`, `surface`»
- Код: `storage/` (библиотека `femstorage`: `json.h`, `sha256.h`, `blob_store.h`, `object_data_codec.h`,
  `project_format.h`, `project.h`, `session.h`), `core/include/fem/core/model/contents.h`, `Document::replace`,
  `CommandBus::replace_document`, `ModelChange::Cause::load`, `core/include/fem/core/text/number.h`,
  `core/include/fem/core/io/files.h`, настройка `project.autosaveInterval`, `python/stresslab/project.py`,
  `python/bindings/src/project.cpp`, `shell/src/project_actions.cpp`, `app/src/` (`Application::project`,
  `stresslab <папка.slproj>`), golden-проект `tests/data/projects/basic.slproj`

## Контекст

До задачи 2.1 модель жила только в памяти. Этап 2 строит на папке проекта историю (2.3), дифф (2.4), кэш
результатов и `.slpack` (2.5), поэтому формат должен сразу давать одинаковые байты для одинаковой модели
(иначе git покажет «изменения», которых нет) и не мешать будущим блокам HDF5 (2.2). Нужно было решить, как
модель попадает в документ при открытии: после задачи 1.3 менять `Document` можно только командами, а
загрузка — не изменение модели и не шаг undo.

## Решения

1. **Раскладка папки.**

   ```
   wing.slproj/
   ├── project.json        {"format": 1, "modules": {...}, "nextObjectId": 13, "units": {...}}
   ├── model/<type>/<id>.json                 объекты ядра (mesh, node_set, element_set, surface)
   ├── model/ext/<owner>/<type>/<id>.json     объекты модулей, включённых и выключенных
   ├── refs/blobs.json     {"<id объекта>": "sha256:<hex>"}
   └── .fem/objects/sha256/<2 hex>/<62 hex>   блоки массивов
   ```

   - **Файл объекта называется по id**, а не по имени: переименование меняет одну строку, а не путь файла;
     нет проблем с регистром (`Top`/`top`), кириллицей и нормализацией NFC/NFD на macOS. Цена — папку
     неудобно читать глазами; показывать модель людям будет дифф в терминах модели (2.4).
   - Owner и type в пути: символы вне `[A-Za-z0-9._-]`, точка в начале и в конце и первая буква имён
     устройств Windows (`aux`, `con`, `com1`...) пишутся как `%XX`. Папки `Note/` и `note/` на Windows и macOS
     сливаются — это безвредно: имена файлов уникальны (id), тип читается из содержимого, а «лишний» файл при
     сохранении определяется сравнением файлов (`fs::equivalent`), а не строк путей.
   - Объекты всех модулей лежат в `model/ext/<owner>/`, в том числе встроенного `fem.model.structural`
     (в архитектуре пример `model/materials/` — до разделения на модули). Правило одно для всех модулей и не
     требует от манифеста объявлять папки.
   - Порядок детей не хранится: в `Document` он равен порядку id (объекты не перемещаются, отмена удаления
     возвращает объект на прежнее место). Это закреплено тестом `ModelLoad.ChildrenAreInIdOrderAfterAnyHistory`;
     появится перемещение объектов — порядок придётся хранить.
   - `nextObjectId` хранится, чтобы id удалённых объектов не выдавались повторно (ADR 0002 п. 2) и журнал
     после открытия проекта воспроизводился с теми же id. Ветки 2.3 будут расходиться в этом числе — это
     конфликт слияния, а слияние отложено до этапа 7.
   - `modules` — владельцы объектов документа с версиями установленных модулей; для неустановленного модуля
     сохраняется версия из открытого проекта, неизвестная — `""`. `fem.core` получает версию платформы.
   - Файл объекта: `id`, `type`, `owner`, `schemaVersion`, `name`, `parent` (`null` у корня),
     `dependencies` (отсортированы), `properties` и, если у объекта есть массивы, `data`
     (`{"kind": "mesh", "nodes": N, "elements": M}` или `{"kind": "node_set", "size": N}`). Счётчики нужны
     диффу 2.4 без чтения блока и проверяются при загрузке. Неизвестные члены — ошибка: новые поля меняют
     `format`.

2. **Канонический JSON — свой писатель поверх nlohmann.** Ключи отсортированы побайтно (это порядок кодовых
   точек UTF-8), отступ 2 пробела, `\n`, финальный перевод строки, UTF-8 без BOM, экранируются только `"`, `\`
   и управляющие символы. Числа с плавающей точкой — кратчайшая запись, читающаяся в тот же double, всегда с
   точкой или экспонентой (`1.0`, `1e+100`, `5e-324`, `-0.0`), чтобы float не превращался в целое. Формат тот
   же, что у `repr` Python в журнале: функция вынесена из `python_literal.cpp` в публичный
   `fem::text::format_double`. `dump()` nlohmann не годится: его Grisu2 не всегда даёт кратчайшую запись.
   При чтении допускаются BOM и `\r\n` (checkout git с `core.autocrlf`), запись всегда каноническая.

3. **Массивы — блоки по хэшу уже в 2.1, простым кодеком.** Иначе Ctrl/Cmd+S не сохранял бы сетки до 2.2.
   `BlobStore` (`put` → `sha256:…`, `get` с проверкой хэша) и `FolderBlobStore` в `.fem/objects`; кодек
   версии 1: `SLDATA\0\0`, версия, вид, массивы с длиной `uint64`, всё little-endian побайтно, без сжатия.
   SHA-256 — своя реализация по FIPS 180-4 (около 150 строк, тесты на векторах NIST), без новой зависимости.
   Задача 2.2 заменит кодек (HDF5, zstd, нарезка) и добавит сборку мусора за тем же интерфейсом; блоки
   версии 1 она либо читает, либо объявляет новый `format` — пользователей формата пока нет.
   `refs/blobs.json` отдельно от файлов объектов: это единый список достижимых блоков для сборки мусора и
   упаковки, без разбора модели.

4. **Загрузка мимо шины: `CommandBus::replace_document(DocumentContents, journal_entry)`.**
   `DocumentContents` — единицы, `next_id` и объекты с их id. `Document::replace` строит состояние во
   временном документе с теми же проверками, что у создания объектов (вид, имя, свойства, данные и сетка
   набора, циклы зависимостей), но разрешает объекты выключенных модулей и зависимости на id удалённых
   объектов; при ошибке документ не меняется. Включённые модули — состояние сеанса, они сохраняются. Шина
   очищает undo и redo (их шаги относятся к старому содержимому), пишет строку журнала и шлёт
   `ModelChange::Cause::load`; summary перечисляет новые объекты как created, совпавшие по id — как updated.
   Дерево модели и панель свойств при `load` перечитывают всё: под тем же id может быть другой объект.

5. **`storage::ProjectSession` — проект документа без Qt.** Папка, флаг «есть несохранённые изменения»
   (любое `ModelChange`, кроме `load`), `open`, `save`, `save_as` (дописывает `.slproj`), `close`, `autosave`.
   Сохранение пишет только изменившиеся файлы, каждый атомарно (временный файл + rename,
   `fem::io::write_file`, заголовок вынесен из `core/src` в публичный), `project.json` последним, затем удаляет
   файлы удалённых объектов и пустые папки; сохранение неизменённой модели не пишет ничего. В чужую непустую
   папку проект не пишется. `open`, `save`, `save_as`, `close` пишутся в журнал строками
   `stresslab.project.…(...)`, автосохранение — нет. Внутри команды или транзакции действия запрещены
   (`CommandError(invalid_state)`), автосохранение их пропускает. Ошибка модели при открытии превращается в
   `ProjectError(invalid_model)` с файлом объекта.

6. **Где живёт сеанс.** `Application` владеет `ProjectSession` с версиями из Extension Manager; окно и
   headless отдают его Python (`Interpreter::attach(..., project)`). У документов, созданных в Python, и у
   документа `stresslab --python` — свой сеанс, созданный вместе с хэндлом. `stresslab.project`: `open`,
   `save`, `save_as`, `close`, `folder`, `is_modified`; ошибки — `stresslab.ProjectError` с `code`, `file`,
   `line`.

7. **Окно.** `ProjectActions`: «Открыть проект…» (`QKeySequence::Open`), «Сохранить» (`QKeySequence::Save`,
   без папки спрашивает место), «Сохранить как…» без сочетания: Ctrl/Cmd+Shift+S в interface-design §12
   отдано «Зафиксировать версию». Автосохранение по таймеру из настройки `project.autosaveInterval` (секунды,
   по умолчанию 60, 0 — выкл.), только при наличии папки и изменений. Заголовок `имя[*] — StressLab`. Вопрос
   «Сохранить / Не сохранять / Отмена» перед закрытием окна и открытием другого проекта. Ошибки не модальные:
   «Проблемы» и строка-подсказка, подробности — в лог. `stresslab <папка.slproj>` открывает проект при старте;
   аргумент без расширения `.slproj` по-прежнему ошибка (скрипт без `run-script`).

## Рассмотренные альтернативы

- **Имя файла из имени объекта (`al-2024.12.json`).** Читается лучше, но переименование объекта — переименование
  файла в истории, а кириллические имена всё равно дают только id.
- **Массивы в JSON до задачи 2.2.** Проще, но наборы на сотни тысяч индексов раздули бы файлы и диффы, и формат
  пришлось бы ломать через одну задачу.
- **Загрузка командой `model.load`.** Тогда загрузка стала бы шагом undo, а журнал содержал бы всю модель.
- **Конструктор `Document` из `DocumentContents`.** `Document` не перемещается: шина, ключи и окно держат на него
  ссылки, поэтому содержимое заменяется на месте.
- **OpenSSL/picosha2 для SHA-256.** Лишняя зависимость ради одной функции; 2.2 может заменить реализацию.

## Последствия

- Каждый новый тип объекта и каждое новое поле получают round-trip тест (CLAUDE.md, правило 6); тест-свойство
  `StorageRoundTrip.*` прогоняет 200 случайных моделей на тип, а `StorageProjectFolder.Golden*` ловит дрейф
  формата (обновление: `STRESSLAB_UPDATE_GOLDEN=1`).
- Многофайловое сохранение не атомарно целиком: сбой посреди него оставляет смесь старых и новых файлов,
  каждый из которых цел (бэклог: восстановление; до 2.3 спасает история, после — коммит).
- Безымянный проект автосохранением не защищён (бэклог: папка восстановления).
- Настройки уровня проекта (`settings::Level::project`) в папку проекта пока не пишутся — пункт бэклога о
  настройках в журнале и в проекте остаётся открытым.
- Задача 2.2 меняет кодек блоков и, вероятно, `format`; 2.3 кладёт `.fem/git` рядом с `.fem/objects`.
