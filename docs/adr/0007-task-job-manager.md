# ADR 0007. Task, пул потоков и Job Manager

- Статус: принято
- Дата: 2026-10-12
- Источник: `docs/architecture.md` §4.6 п. 7 и §6, задача 1.6 из `docs/plan.md`
- Код: `core/include/fem/core/task/` (`fem::task`), `core/include/fem/core/job/` (`fem::job`),
  `core/include/fem/core/concurrent_signal.h`

## Контекст

С задачи 1.3 команда может вернуть `Task` в `CommandResult::task`, но это была пустая заглушка (ADR 0004
п. 12). Архитектура требует: долгие операции (импорт, мешинг, расчёт) асинхронны, с прогрессом, сообщениями и
отменой (правило 7 CLAUDE.md); адаптер решателя не запускает процессы сам, а описывает задание, а Job Manager
решает, где его выполнить, — сейчас на этом компьютере, позже по SSH, через Slurm/PBS или в облаке (правило 8,
§6). Открытыми оставались: кто владеет задачей и кто её завершает, как отмена доходит до процесса, на каком
потоке приходят события, что считать успехом задания и как убить всё дерево процессов на трёх ОС.

## Решения

1. **Две стороны задачи.** `Task` — сторона вызывающего (оболочка, Python, тест): состояние
   `pending → running → succeeded | failed | cancelled`, прогресс 0..1 или неопределённый (`nullopt`),
   сообщения с важностью, `cancel()`, `wait()`/`wait_for()`, `result()`. `TaskControl` — сторона работы:
   `start`, `set_progress`, `message`, `on_cancel`, `succeed`/`fail`/`finish_cancelled`. Создаётся
   `make_task(title)` или `TaskPool::submit`; `Task` не наследуется. Так в задачу нельзя «дописать прогресс»
   снаружи, а исполнитель не может её отменить за пользователя.
2. **`result()` как у `std::future::get`.** Значение — `command::Value` (то же, что возвращает команда и
   увидит Python в 1.8); у упавшей задачи `result()` бросает то, что бросила работа (`JobError`, исключение
   модуля), у отменённой — `TaskCancelled`, у незавершённой — `TaskError(not_finished)`. Коды ошибок —
   перечисления, текст для пользователя делает локализация (как в остальных подсистемах).
3. **Отмена как в .NET.** `cancel()` ставит флаг и один раз вызывает колбэки `on_cancel` на потоке, который
   отменяет. Задача в очереди отменяется сразу и не запускается (`start()` вернёт `false`). Работа, которая
   после запроса всё же вернула результат, — `succeeded`: готовый результат не выбрасывается. Колбэки забываются
   при завершении (они держат процессы и т. п.).
4. **Брошенная задача не висит.** Когда последняя копия `TaskControl` уничтожена, а задача не завершена, она
   падает с `TaskError(abandoned)` (как `broken_promise`). Оболочка никогда не показывает вечный «идёт».
5. **События на потоке, который изменил задачу.** Задачи меняются на рабочих потоках, а модель и context keys
   однопоточны. Ядро не тащит свой цикл событий: слушатель вызывается на рабочем потоке, вне блокировок задачи,
   и оболочка сама переносит уведомление в свой поток (Qt queued connection). Для этого
   `ConcurrentSignal` — потокобезопасный вариант `Signal`: после `Subscription::reset()` слушатель не
   выполняется и больше не вызывается, поэтому объект может отписаться в деструкторе.
6. **`TaskPool`** — фиксированное число потоков (по умолчанию по числу аппаратных), FIFO. Функция работы
   получает `TaskControl&`, её значение — результат; `TaskCancelled` отменяет, любое другое исключение —
   `failed`. Деструктор отменяет всё и ждёт.
7. **«Что» и «где» разделены.** `JobSpec` — программа, аргументы (без shell), окружение (задать/убрать поверх
   унаследованного или без наследования), рабочая папка, входные и выходные файлы; ссылок на исполнителя в нём
   нет, поэтому его можно сериализовать и отправить куда угодно. `Executor::start(spec, sink)` →
   `Execution{cancel(), wait()}`; вывод приходит кусками в `OutputSink`. Удалённый исполнитель реализует тот же
   интерфейс: `start` — отправить (скопировав входы), `wait` — опрашивать и забрать выходы, `cancel` — `scancel`.
   `workdir` — всегда локальная папка; где программа работает на самом деле, знает только исполнитель.
8. **Job Manager.** Исполнители регистрируются по id (`local`, позже `ssh:…`, `slurm:…`), первый — по
   умолчанию; у каждого своя очередь FIFO и предел `max_parallel` (для локального по умолчанию 1: решатель
   сам занимает все ядра). `submit(spec, {executor, on_line})` → `Job`, у которого `task()` — обычная `Task`:
   её можно вернуть из команды, отмена через неё останавливает процесс. Каждое запущенное задание — свой поток
   ожидания.
9. **Успех задания** — код 0 и все `outputs` на месте; результат `{"exitCode": 0}`. Иначе `JobError`:
   `launch_failed`/`missing_input` (не запустилось), `exit_code` (другой код или сигнал), `missing_output`.
   Отменённое задание, которое всё же завершилось с кодом 0, считается успешным (п. 3). Ошибки самого
   `JobSpec` не бросаются из `submit`, а завершают задачу: оболочка показывает их в «Заданиях» как любой сбой.
10. **Строки и прогресс.** Менеджер режет вывод на строки (`\n`, `\r\n`, хвост без перевода строки), длинные
    режет по 64 КиБ на границе символа UTF-8, байты не перекодирует. `on_line(line, TaskControl&)` — место для
    `parse_progress` адаптера: менеджер ничего не знает о форматах решателей (правило 1). Исключение из
    `on_line` не останавливает расчёт, а один раз становится предупреждением задачи. В памяти — хвост из
    `log_tail_lines` строк (10 000), полный поток — через `subscribe_log`.
11. **Дерево процессов.** Windows: процесс создаётся приостановленным, помещается в Job Object с
    `KILL_ON_JOB_CLOSE`, затем запускается; отмена — `TerminateJobObject`. Наследуются только наши три
    дескриптора (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`), stdin — `NUL`, окно консоли не создаётся. Командная строка
    экранируется по правилам `CommandLineToArgvW`; `.bat`/`.cmd` не запускаются напрямую (cmd.exe разбирает
    аргументы иначе, BatBadBut) — задание явно вызывает `cmd.exe`. POSIX: `fork` + `execve` в свою группу
    процессов, всё для потомка готовится до `fork`, ошибка `chdir`/`exec` возвращается через close-on-exec
    канал; отмена — `SIGTERM` группе, через `terminate_grace` (3 с) — `SIGKILL`. Лидер ждётся через
    `waitid(WNOWAIT)`, чтобы добить группу, пока её id не может занять чужой процесс.
12. **Задание кончается вместе с программой.** Когда главный процесс завершился, оставшиеся в его Job Object или
    группе процессы убиваются: иначе потомок, унаследовавший stdout, не дал бы закончиться чтению, а задание
    «закончилось бы» с живыми процессами. Решатели, которые уходят в фон (`abaqus job=…` без `interactive`),
    запускаются адаптером в режиме ожидания.
13. **Программа по имени** ищется в `PATH` окружения задания, а не приложения (на Windows с `.exe`/`.com`);
    путь с папками без корня берётся от `workdir`. Имена переменных на Windows сравниваются без учёта регистра.

## Рассмотренные альтернативы

- **`std::future`/`std::async`** — нет прогресса, сообщений и отмены, а `std::async` не даёт управлять
  потоками.
- **Свой цикл событий в ядре** (очередь событий, которую главный поток разбирает `process_events()`) — ядро
  стало бы диктовать оболочке и headless-режиму, как жить; у Qt цикл уже есть. Можно добавить позже как
  адаптер поверх `subscribe`.
- **Отмена отменяет всегда, даже успевшую работу** — проще объяснить, но выбрасывает готовые результаты
  длинного расчёта из-за поздно нажатой кнопки.
- **`posix_spawn`** — нет переносимого `chdir` (`posix_spawn_file_actions_addchdir_np` нестандартен), и ошибку
  `exec` он сообщает хуже; `fork` с одними async-signal-safe вызовами в потомке надёжен.
- **Убивать только главный процесс** — потомки (MPI, обёртки решателей) остаются и держат лицензии и файлы.
- **cgroups (Linux) / `PR_SET_CHILD_SUBREAPER`** — ловят и процессы, ушедшие из группы через `setsid`, но
  только на Linux и с привилегиями; для решателей группы достаточно.
- **Хранить весь лог в памяти** — вывод решателя бывает в сотни мегабайт.

## Последствия

- Адаптеры решателей (3.5) отдают `JobSpec` из `write_input`, а `parse_progress` вешают на `on_line`;
  `detect()` может запускать короткие задания тем же менеджером.
- Оболочка (1.11/1.12) показывает `JobManager::jobs()` во вкладке «Задания», подписывается на
  `on_submitted`, `Task::subscribe` и `Job::subscribe_log` и переносит события в поток GUI. Ключи
  `job.*` (ADR 0005 отдаёт их Job Manager) не сделаны: их меняют события рабочих потоков, а ключи меняются
  только в потоке модели — их выставляет тот, кто переносит события (`docs/backlog.md`).
- Python API (1.8) оборачивает `Task` (прогресс, отмена, `result()`); headless-режим (1.10) ждёт задачи,
  которые вернули команды скрипта.
- Удалённый исполнитель — новый класс `Executor` и его регистрация; `JobSpec` для этого понадобится
  сериализовать (детерминированный JSON, правило 6).
- Процесс, сам ушедший из группы (`setsid`), на POSIX не убивается; на Windows из Job Object можно выйти
  только с разрешённым breakaway, которого мы не даём.
