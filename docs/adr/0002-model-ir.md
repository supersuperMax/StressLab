# ADR 0002. Базовая модель данных (Model IR)

- Статус: принято
- Дата: 2026-10-12
- Источник: `docs/architecture.md` §3 и §4.6 п. 4, задача 1.2 из `docs/plan.md`
- Код: `core/include/fem/core/model/`, пространство имён `fem::model`

## Контекст

Ядру нужна модель данных, через которую общаются все модули: дерево объектов с владельцами-модулями,
зависимости между объектами, сетка большого размера без лишних копий, явные единицы и сохранность объектов
выключенных модулей. Архитектура задаёт требования, но оставляет открытыми устройство идентификаторов,
нумерацию узлов в элементах, место наборов и поведение ссылок на удалённые объекты.

## Решения

1. **Объект** — `id`, `type`, `owner`, `schema_version` (≥ 1), `name`, `properties`, родитель, дети
   (в порядке создания), зависимости и необязательные неизменяемые данные (`ObjectData`).
   `owner` — модуль, который *определяет тип* объекта, а не тот, кто его создал: сетку, построенную
   мешером, всё равно понимает ядро (`owner = "fem.core"`), поэтому выключение мешера её не прячет.
   `properties` — `nlohmann::json`-объект; при записи ядро требует конечные числа, корректный UTF-8 и
   отсутствие бинарных значений, чтобы сериализация 2.1 была детерминированной.
   Непустое имя уникально среди соседей того же типа (с учётом регистра).

2. **`ObjectId`** — 64-битное число, документ выдаёт id по возрастанию и не переиспользует их.
   Последовательные id (а не UUID) нужны, чтобы журнал команд (1.3), выполненный в новом документе,
   давал тот же документ. Возможные совпадения id в двух ветках проекта решаются при слиянии (этап 7).

3. **Зависимости** — явные рёбра в зависимом объекте, а не ссылки внутри `properties`: ядро не знает схем
   модулей, но обязано знать зависимости непрозрачных объектов. Ссылки на себя, на отсутствующие объекты и
   циклы запрещены. Если удаляется объект, от которого зависит *активный* объект, зависимость остаётся
   «висячей» (`Document::missing_dependencies`): модуль покажет ошибку и даст её исправить, как в CAE-системах;
   undo вернёт объект без дополнительной работы.

4. **Непрозрачные объекты.** Объект непрозрачен, если его модуль не включён в документе
   (`Document::set_owner_enabled`). Неизвестные модули по умолчанию выключены: модель с объектами
   неустановленного модуля открывается без риска их испортить. Ядро всегда включено. Включение модуля —
   не изменение модели и через Command Bus не проходит. Ядро запрещает менять непрозрачный объект и
   добавлять ему детей, удалять его (в том числе вместе с предком) и удалять то, от чего он зависит.
   Причина отказа возвращается данными (`RemovalBlocker`: что удаляется, какой непрозрачный объект мешает и
   почему), текст для пользователя строится через локализацию (задача 1.7).

5. **Сетка** — объект типа `mesh` с данными `Mesh`: узлы в SoA (`x`, `y`, `z` типа `double`, метки
   `int64`), блоки элементов одного типа со связностью в виде 0-based индексов узлов (`int32`). Массивы
   передаются move-ом, наружу отдаются как `std::span`; `Mesh` неизменяем и разделяется через
   `std::shared_ptr<const Mesh>` (undo, Python-представления, хранилище блоков по хэшу). Ограничение
   `int32`-индексов — 2³¹ − 1 узлов и элементов на сетку; при необходимости меняется один псевдоним `Index`.

6. **Наборы узлов, элементов и поверхностей — отдельные объекты, дети своей сетки** (`node_set`,
   `element_set`, `surface`), а не поля `Mesh`. Так нагрузка зависит от конкретного набора, правило п. 4
   работает для наборов, а раскладка проекта `model/sets/…` (архитектура §3.1) и дифф по объектам
   получаются без особых случаев. Наборы хранят отсортированные уникальные индексы и проверяются против
   сетки-родителя при создании и при замене сетки. Это уточнение архитектуры §3, где наборы перечислены
   внутри Mesh: по смыслу они по-прежнему часть сетки.

7. **Нейтральная нумерация — порядок узлов VTK** (он же внутренний порядок meshio). Типы: `vertex`,
   `line2/3`, `tri3/6`, `quad4/8`, `tet4/10`, `pyramid5/13`, `wedge6/15`, `hex8/20`; тип описывает только
   топологию, формулировка элемента (оболочка, балка, редуцированное интегрирование) — дело модулей
   (задача 3.1). Квадратичные типы: сначала углы, затем по узлу на ребро в порядке таблицы рёбер.
   Стороны (для поверхностей): грани 3D-элементов в порядке и с внешней нормалью VTK, рёбра 2D-элементов,
   концы 1D-элементов. Выбор VTK: просмотрщик (3.7) и импорт через meshio (§5) работают без перестановок;
   форматы с другим порядком (например, другая ориентация клина) переставляют узлы в своих модулях.

8. **Единицы** — `UnitSystem` из единиц длины, массы, времени и температуры; производные единицы
   (сила, напряжение, плотность) следуют из них, поэтому модель согласована по построению. Документ всегда
   хранит систему явно (по умолчанию СИ); `set_units` значения не пересчитывает.

## Рассмотренные альтернативы

- **UUID вместо последовательных id** — проще слияние веток, но журнал перестаёт воспроизводиться побайтно.
- **Строгая ссылочная целостность** (запрет удалять любой объект, от которого кто-то зависит) — отказ
  пришлось бы обходить каскадами в каждой команде, а пользователь CAE ожидает «нагрузка без набора ✕».
- **Наборы внутри `Mesh`** — нельзя зависеть от отдельного набора, и правило п. 4 для наборов потребовало
  бы адресации «объект + имя внутри него».
- **Своя нумерация или нумерация Gmsh** — лишние перестановки в просмотрщике и при импорте через meshio.

## Последствия

- Сериализация и round-trip тесты для сетки и наборов появятся вместе с хранилищем (задачи 2.1, 2.2).
- Прямые изменения `Document` в задаче 1.3 закрываются Command Bus. Методы изменения уже атомарны (при
  ошибке документ не меняется); восстановление удалённого поддерева с прежними id для undo добавит 1.3.
- Данные модулей (`ObjectData`) пока разрешены только типам ядра; когда модулям понадобятся большие
  массивы (результаты, задача 3.1), правило ослабляется отдельным решением.
