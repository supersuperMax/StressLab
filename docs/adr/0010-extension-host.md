# ADR 0010. Extension host python-модулей и протокол внепроцессных модулей

- Статус: принято
- Дата: 2026-10-13
- Источник: `docs/architecture.md` §4.4, §4.5, задача 1.9 из `docs/plan.md`
- Код: `core/include/fem/core/ipc/` (`fem::ipc`: JSON-RPC, shared memory),
  `core/include/fem/core/extension/host_runtime.h` (`HostRuntime`), `LocalExecutor::start_interactive`
  (`core/include/fem/core/job/local_executor.h`), пакет `python/stresslab_host/`
- Протокол: `docs/extensions/protocol.md`

## Контекст

С задачи 1.5 python- и process-модули включаются декларативно (меню, команды на шине, ключи), но активировать
их нечем: ADR 0006 п. 10 оставил `ExtensionRuntime` для них на 1.9. Архитектура (§4.4) требует: код таких
модулей работает вне процесса приложения, обмен — JSON-RPC поверх stdio, как в LSP, большие массивы — через
shared memory или HDF5, падение или зависание модуля не трогает приложение и несохранённую модель; у каждого
python-модуля свои зависимости (§4.5). Открытыми были: один хост на все модули или на каждый, что делать с
однопоточной моделью, когда модуль зовёт приложение из своего потока, как отличить зависание от долгой работы,
как передавать массивы на трёх ОС и что видит пользователь.

## Решения

1. **Один процесс на модуль.** Каждый активный python-модуль работает в своём процессе хоста
   (`python -m stresslab_host`), process-модуль — в своём исполняемом файле. Так `site-packages` и
   `sys.modules` модулей не смешиваются (два модуля могут требовать разные версии одной библиотеки), а падение
   одного модуля перезапускает только его. Цена — память и время запуска интерпретатора на модуль (десятки
   мегабайт и доли секунды; модуль запускается только при активации, ADR 0006 п. 1). Это расхождение с §4.4
   («в отдельном extension host процессе (как в VSCode)» — у VS Code хост общий): общий хост для группы
   модулей возможен позже без изменения протокола — записано в бэклог.
2. **Один протокол для python и process.** JSON-RPC 2.0 в кадрах LSP (`Content-Length`), UTF-8, stdout —
   только протокол, stderr — в лог приложения (категория `extension`, строка с id модуля; последние 20 строк
   попадают в отчёт о падении). Хост на Python переносит fd 1 на fd 2 при старте, так что `print` модуля и
   вывод C-библиотек не ломают поток. `HostRuntime` реализует `ExtensionRuntime` и регистрируется через
   `set_runtime` для обоих видов; различаются только запуск (`HostLauncher`) и параметры `initialize`.
3. **Запуск описывается `JobSpec`, а стартует локально** новым `LocalExecutor::start_interactive` — тот же
   Job Object / группа процессов, что в 1.6, плюс канал stdin. Хост обязан быть на этом компьютере (каналы и
   shared memory), поэтому удалённого исполнителя здесь нет, но «что запустить» отделено от «где» (правило 8).
   POSIX: stdin — `socketpair`, запись с `MSG_NOSIGNAL` (Linux) или `SO_NOSIGPIPE` (macOS) — запись в упавший
   модуль не даёт SIGPIPE и не трогает обработку сигналов приложения. Windows: обычный pipe.
4. **Потоки.** Модель однопоточна. Вывод модуля читают потоки исполнителя, писатель с очередью отправляет
   сообщения (модуль, который перестал читать, не блокирует приложение), поток-монитор ждёт конца процесса.
   Пока выполняется команда модуля, главный поток ждёт ответа и сам выполняет запросы модуля к этому вызову
   (`call/execute`, `call/createObject`, чтение модели, ключи) — вложенные команды и изменения модели входят в
   тот же шаг undo, исключение откатывает всё. Модуль может снова вызвать свою же команду через приложение:
   обе стороны обслуживают входящие запросы, пока ждут ответа. Запросы вне вызова (из фоновой работы модуля)
   ждут `HostRuntime::poll()`, которую приложение вызывает в потоке модели; `on_pending` (потокобезопасный
   сигнал) будит его цикл. Команда модуля «сама по себе» (`command/execute` от модуля) никогда не выполняется
   внутри другой команды — она откладывается до `poll`. Прогресс задач идёт сразу из потока чтения
   (`TaskControl` потокобезопасен).
5. **Падение и зависание.** Падение — конец процесса (или нарушение протокола, после которого процесс
   завершается). Зависание — (а) за `call_timeout` (30 с) модуль не прислал ничего, относящегося к текущему
   вызову: ответов, запросов (ответы на ping не считаются — хост на Python отвечает на них из потока чтения, даже
   когда команда крутит бесконечный цикл); время, которое приложение само тратит на вложенные запросы, не
   считается; (б) watchdog: модуль не ответил на `$/ping` за `ping_timeout` (10 с; ping каждые 5 с) — ловит
   процесс, который перестал читать совсем. Долгая работа — это Task (правило 7), а не долгий синхронный
   вызов. Итог одинаков: процесс завершается вместе с деревом, ждущая команда бросает
   `ExtensionError(command_failed)` — шина откатывает её изменения, модель и стек undo целы, — задачи модуля
   падают, сегменты shared memory освобождаются, процесс запускается заново и модуль активируется снова
   (сразу в `execute` или `poll`, иначе лениво при следующей команде). После `restart_limit` (3) остановок за
   `restart_window` (5 мин) модуль не перезапускается, его команды отказывают до выключения/включения.
6. **Сообщение пользователю** — событие менеджера `extension.crashed` с `CrashReport` (причина
   `crashed|hung`, перезапущен ли, сколько раз подряд, подробности для лога: код выхода, хвост stderr,
   команда). Runtime сообщает через новый `ExtensionHost::report_crash`, менеджер пишет в лог и рассылает
   событие; текст для пользователя — `crash_message(info, report, localization)` из строк ядра
   `extension.crashed`, `extension.hung`, `extension.gaveUp` (ru/en, с формами множественного числа). Показ
   уведомления — оболочка (1.12) и headless (1.10).
7. **Большие массивы — shared memory на всех трёх ОС, HDF5 не нужен.** Windows — именованный file mapping в
   файле подкачки, macOS и Linux — POSIX `shm_open` + `mmap` (`fem::ipc::SharedMemory`). Неудобств, ради которых
   задача допускала временный HDF5, не нашлось: имена на macOS ограничены 31 символом (имена короткие:
   `sl<pid>_<n>_<соль>` и `slh<pid>_<12 hex>`), на Linux `shm_open` до glibc 2.34 в `librt` (линкуется).
   HDF5 дал бы лишние запись и чтение файла и зависимость хоста от h5py. Массив в сообщении —
   `{"shm", "offset", "dtype": "f8|i8|i4", "count"}` или список JSON. Модуль сообщает в `initialize`
   `capabilities.sharedMemory`; без неё (process-модуль на другом языке) приложение пишет массивы в сообщение,
   и маленькие (< 4 КиБ вместе) — всегда так. Модуль → приложение: модуль создаёт сегмент, приложение
   копирует массивы в векторы ядра (одна копия неизбежна: данные Model IR — `std::vector`, ADR 0002), модуль
   удаляет сегмент после ответа. Приложение → модуль: приложение кладёт все массивы ответа в один сегмент, хост
   отображает его и сразу шлёт `shm/release` — приложение удаляет имя, а память живёт, пока её держат
   numpy-массивы хоста (только для чтения, без копии). Сегменты упавшего модуля освобождаются.
   `multiprocessing.shared_memory` в хосте не используется: в Python 3.12 он регистрирует каждый открытый
   сегмент в resource tracker (отдельный процесс), который удаляет чужие сегменты при выходе (`track=False`
   появился только в 3.13). Хост работает с `mmap` и `_posixshmem` — модулем стандартной библиотеки CPython, на
   котором построен `multiprocessing.shared_memory`.
8. **API модуля в хосте — отдельный пакет `stresslab_host`**, а не `stresslab`: тот работает с документом
   своего процесса (ADR 0009 п. 3), а в хосте документ — в приложении. Отклонение от прогноза ADR 0009
   («1.9 переиспользует `stresslab` в процессе хоста»): прокси `stresslab` поверх протокола — в бэклоге.
   `entry = "пакет.модуль:activate"` → `activate(extension)`; `extension.command(id)` /
   `register_command` (только команды из манифеста, проверяет приложение — `contributions/register`),
   `extension.context` (`declare`, `set`, `evaluate`, `watch`), `on_model_changed`, `execute` (команда сама
   по себе), чтение модели (`object`, `objects`, `data`). Обработчик команды получает `Call`: `args`,
   `execute`, `create_object`, `set_data`, чтение модели, `run_task(title, work)` — задача стартует в своём
   потоке после ответа, поэтому её уведомления всегда идут после ответа, который её объявил.
   `deactivate()` модуля вызывается при выключении (`shutdown`). numpy импортируется только когда модулю нужны
   массивы.
9. **Свой `site-packages`.** Хост ставит первыми в `sys.path` папку модуля, `<папка модуля>/site-packages`
   (зависимости, поставляемые с модулем) и `<HostRuntimeOptions::user_site_packages>/<id>/site-packages`
   (куда их поставит менеджер модулей), затем свою папку, стандартную библиотеку и site-packages базового
   Python; записи из `PYTHONPATH` (кроме папки хоста), пользовательский site-packages и текущая папка
   убираются. Файлы `.pth` в site-packages модуля пока не обрабатываются; установка зависимостей (pip
   `--target`) — задача менеджера модулей (бэклог).
10. **Запуск хоста в продукте** — тем же встроенным Python: `stresslab --python -m stresslab_host`
    (`python_launcher`); `stresslab_host` копируется в `build/<пресет>/python/site` рядом со `stresslab`.
    В тестах ядра — обычный Python сборки (`python -m stresslab_host`), один тест — через `stresslab`.
    Переменные `PYTHONUTF8=1` и `PYTHONIOENCODING=utf-8` задаются всегда.
11. **Что модуль может в приложении** (подробно — `docs/extensions/protocol.md`): регистрация кода команд;
    объявление, установка, вычисление и подписка на ключи (`context/watch` с `when`-выражением → уведомления
    `context/changed`); подписка на изменения модели (`model/changed` после каждого шага); чтение объектов и их
    данных; изменения модели только внутри вызова своей команды или командами. Задачи: `task/progress`,
    `task/message`, `task/finished`, отмена — `task/cancel`. Порядок выключения: `shutdown` → `exit` →
    закрыть stdin → через `shutdown_timeout` завершить процесс.

## Рассмотренные альтернативы

- **Общий хост на все python-модули** (как VS Code) — экономит память, но зависимости модулей конфликтуют в
  одном `sys.modules`, а падение одного модуля перезапускает все. Можно добавить как группировку позже.
- **Сокет или именованный канал вместо stdio** — ничего не даёт локально, а stdio одинаков на трёх ОС и у
  любого языка; `docs/architecture.md` §4.4 допускает оба.
- **Временные HDF5-файлы для массивов** — см. п. 7: лишний ввод-вывод и зависимость, без выигрыша на какой-либо
  ОС.
- **Массивы прямо в JSON** — 1 млн узлов — десятки мегабайт текста и секунды разбора; оставлено только для
  маленьких массивов и модулей без shared memory.
- **Выполнять запросы модуля на потоке чтения** — модель однопоточна; блокировка всей модели сделала бы
  повторный вход (модуль → приложение → модуль) взаимной блокировкой.
- **Общий таймаут на всю команду** вместо таймаута бездействия — ломал бы команды из многих коротких вложенных
  вызовов; ping без таймаута вызова не ловил бы бесконечный цикл в Python (ping отвечает поток чтения).
- **SIGPIPE игнорировать во всём приложении** — меняет поведение процесса за пределами ядра; сокет с
  `MSG_NOSIGNAL`/`SO_NOSIGPIPE` решает задачу локально.

## Последствия

- Headless (1.10) и оболочка (1.11–1.12) создают `HostRuntime` с `python_launcher(<stresslab>, {"--python",
  "-m", "stresslab_host"})`, регистрируют его для `python` и `process`, вызывают `poll()` в своём цикле по
  `on_pending` и показывают `crash_message` по событию `extension.crashed`.
- Демонстрационный модуль (1.15) пишется на `stresslab_host`.
- Менеджер модулей (1.14) ставит зависимости в `<user_site_packages>/<id>/site-packages`.
- Новые методы протокола добавляются без смены `protocolVersion`, пока старые не меняют смысла; модуль
  отвечает `method not found` на незнакомое, приложение — тоже.
