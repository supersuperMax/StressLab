# ADR 0006. Extension Manager, реестр contributions и C ABI нативных модулей

- Статус: принято
- Дата: 2026-10-12
- Источник: `docs/architecture.md` §4.1–4.6, задача 1.5 из `docs/plan.md`
- Код: `core/include/fem/core/extension/` (`fem::extension`), `core/include/fem/extension_abi.h`

## Контекст

К задаче 1.5 у ядра есть все стороны, с которыми работает модуль: Model IR с непрозрачными объектами
выключенных модулей (ADR 0002 п. 4), Command Bus с владельцами команд (ADR 0004) и context keys с владельцами
(ADR 0005). Нужен тот, кто читает манифест `stresslab-extension.toml`, проверяет совместимость и
зависимости, наполняет реестр contribution points, загружает код модуля и при выключении убирает всё, что
модуль внёс, без перезапуска. Архитектура задаёт требования (§4.1–4.6), но оставляет открытыми: когда грузить
код, как описать команды без кода, что делать с ошибками в манифесте, какой диалект semver, как устроен C ABI
и где границы для python/process-модулей (задача 1.9).

## Решения

1. **«Включён» и «активен» — разные состояния.** Включение декларативно: записи манифеста попадают в реестр
   (`ContributionRegistry`), команды регистрируются на шине, ключи из манифеста объявляются, объекты модуля
   перестают быть непрозрачными (`Document::set_owner_enabled`). Код не грузится. Активация — загрузка и
   запуск кода — происходит по событию из `activation` (`onStartup`, `onCommand:`, `onOpenFile:`,
   `onSolverRequested:`; в шаблоне `*` — любой текст, `?` — один символ, имя файла сравнивается без учёта
   регистра ASCII) или при первом вызове команды модуля (как в VS Code ≥ 1.74). Так оболочка строит меню и
   палитру по манифестам (§4.6 п. 1), а код модулей, которыми не пользуются, не загружается.
2. **Команды модуля на шине — прокси.** При включении шина получает команду с id, владельцем и схемой
   аргументов из манифеста; её обработчик активирует модуль (и модули, ждущие `onCommand:` этой команды) и
   передаёт вызов коду (`ExtensionInstance::execute`). Шина проверяет аргументы до загрузки кода, журнал и undo
   работают как для любой команды. Активационные события от команд ядра (`model.*`) не приходят: они не
   проходят через прокси.
3. **Выключение** — `deactivate()` кода, снятие команд с шины, удаление ключей и записей реестра этого
   владельца, непрозрачность объектов и событие `extension.deactivated(id)`. Модули, которым нужен
   выключаемый, выключаются первыми (`plan_disable` даёт порядок для предупреждения в оболочке). Выключить
   модуль, чья команда выполняется, нельзя (`invalid_state`). События: `extension.enabled`,
   `extension.activated`, `extension.activationFailed`, `extension.deactivated`.
4. **Зависимости разрешаются при включении.** `enable(id)` включает недостающие модули из `requires`
   («зависимости раньше», обход в глубину, требования по id), `plan_enable` показывает план до подтверждения.
   Ошибки называют цепочку: нет модуля, не та версия, несовместимый `engine` (`unresolved_dependency`),
   цикл (`dependency_cycle`). План включается атомарно: конфликты проверяются заранее на копии реестра,
   против команд на шине и чужих context keys.
5. **Уникальность id.** Id, которые называют что-то общее для приложения, уникальны между модулями:
   команды, этапы, решатели, мешеры, форматы, вкладки, слои, фильтры, иконки, `activityBar`, ключи настроек и
   context keys. Типы объектов (`treeNodeTypes`, `propertySchemas`) принадлежат владельцу (ADR 0002 п. 1) и
   могут повторяться в разных модулях. Реестр перечисляет записи по id владельца, затем в порядке манифеста,
   поэтому порядок меню не зависит от порядка включения.
6. **Манифест разбирается строго.** Неизвестный ключ, неверный тип, пустое обязательное поле, неверный id,
   путь вне папки модуля (`..`, абсолютный), неверное условие `when` — ошибка с номером строки и колонкой
   toml++; `ManifestError` собирает все ошибки файла по порядку. Опечатка в манифесте иначе молча убрала бы
   кнопку. Исключение: если `engine` не принимает текущую версию платформы, проверяются только `id`, `name`,
   `version`, `engine`, а `contributes` не разбирается — модуль для другой версии может использовать
   неизвестные ключи. Такой модуль виден в индексе как несовместимый и не включается.
7. **Версия `engine` — версия платформы** (`fem::version()`, сейчас 0.1.0). Отдельной «версии API» нет, пока
   API не стабилизирован (как `engines.vscode`). Диапазоны — подмножество npm: `^`, `~`, `=`, `>`, `>=`, `<`,
   `<=`, частичные версии (`1`, `1.2`), `*`, пробел = И, `||` = ИЛИ; pre-release подходит только к
   компаратору с pre-release той же тройки. Версии — SemVer 2.0.0, сравнение по его правилам, build metadata
   игнорируется.
8. **Две точки сверх таблицы §4.2.**
   - `contextKeys` (name, type, default): ключи модуля объявляются при включении и удаляются при выключении,
     поэтому условия `when` видят их до загрузки кода. Закрывает пункт бэклога из 1.4 (ADR 0005,
     «Последствия»). Код модуля может объявить и другие ключи через `ExtensionHost`; писать можно только в
     свои.
   - `args` у `commands` (name, type, required, default): Python-сигнатура команды без загрузки кода, которую
     §4.2 требует для каждой команды; из неё же 1.8 сгенерирует обёртки. Проверяется теми же правилами, что
     и на шине (`command::check_spec`).
9. **Записи реестра** — типизированные структуры в `contributions.h`, у каждой `owner`. Строки для
   пользователя (`title`, `label`, `description`) хранятся как в манифесте; подстановка `%key%` и переводы —
   задача 1.7. Схемы `propertySchemas` и описания `settings` хранятся как JSON (inline-таблицы TOML);
   генератор форм и проверка значений — задачи 1.13 и 1.7.
10. **Виды модулей.** Код запускает `ExtensionRuntime` своего вида. В ядре есть runtime нативных модулей;
    runtime python- и process-модулей придёт с extension host (1.9) через `set_runtime`. До этого такие модули
    включаются (их меню и команды видны), а активация сообщает `activationFailed` «нет runtime». Модуль без
    `kind` и `entry` — декларативный (переводы, клавиши, меню для чужих команд): ему нельзя `commands` и
    `activation`.
11. **C ABI** (`fem/extension_abi.h`, чистый C). Библиотека экспортирует `fem_extension_entry()` →
    `FemExtension{struct_size, abi_version, activate, deactivate}`; хозяин даёт `FemHostApi` (id, папка,
    версия платформы, `register_command`, `set_context_key`, `set_error`) и `FemCommandApi` для вызова
    команды (аргументы, результат, ошибка, вложенный `execute`). Значения — текст JSON в UTF-8, строки хозяина
    живут до конца вызова, всё полученное хозяин копирует, исключения через границу не проходят. Модель
    нативный модуль меняет вложенными командами (`model.*` и любыми другими) — undo и журнал работают без
    отдельного API редактирования. Структуры только дописываются (`struct_size` первым полем),
    `FEM_EXTENSION_ABI_VERSION` (сейчас 1) меняется только при несовместимом изменении, библиотеку другой
    версии хозяин не загружает. Имя файла — `entry` плюс `.dll`, `.dylib` или `.so`. Загрузка —
    `LoadLibraryExW` с широким путём (поиск зависимостей рядом с библиотекой, без системных диалогов) или
    `dlopen`.
12. **Нативная библиотека не выгружается до выхода** (§4.6 п. 2): после `deactivate()` она остаётся в
    процессе, повторное включение активирует ту же загруженную библиотеку (`ExtensionInfo::code_loaded`
    показывает это оболочке). Новая версия файла на диске подхватится только после перезапуска.
13. **Индекс.** `scan(root, source)` ставит модули из подпапок по имени; плохие манифесты и повторные id
    попадают в отчёт, а не в исключение. Источник — `builtin`, `user` или `local`; модуль из папки (`local`)
    считается непроверенным, оболочка предупреждает перед включением. Подписей пакетов пока нет (этап 6).
    `command_index()` даёт команды всех установленных модулей с пометкой, включён ли модуль, — для палитры
    (§4.6 п. 8).
14. **Профили** — JSON: `{"extensions": [{"id", "version"}], "format": "stresslab.profile",
    "formatVersion": 1, "layout": {...}, "name"}`; ключи отсортированы, отступ два пробела, UTF-8 как есть, `\n`,
    перевод строки в конце, так что сохранить → загрузить → сохранить даёт те же байты (правило 6).
    `layout` принадлежит оболочке. `apply_profile` выключает модули не из профиля, включает перечисленные с
    зависимостями и сообщает об отсутствующих, о расхождении версий (модуль всё равно включается) и о тех,
    что включить нельзя.

## Рассмотренные альтернативы

- **Грузить код при включении** — проще (нет прокси и событий), но противоречит §4.1 («модуль не грузится,
  пока событие не произошло») и замедляет старт с десятками модулей.
- **Команды регистрирует код модуля** (как `registerCommand` в VS Code) — тогда без загрузки кода нет схемы
  аргументов, палитры с подсказками и Python-обёрток; манифест всё равно пришлось бы дублировать.
- **Предупреждения вместо ошибок для неизвестных ключей** — терпимее к модулям новых версий, но тот же случай
  закрыт исключением для несовместимого `engine`, а для совместимого опечатка важнее.
- **Отказ включать модуль с выключенными зависимостями** (как спрашивает VS Code) — оболочке всё равно нужен
  план «будут включены также …»; менеджер даёт его (`plan_enable`) и выполняет одним вызовом.
- **C++-интерфейс для нативных модулей** — удобнее, но ABI C++ зависит от компилятора и стандартной
  библиотеки; модули сторонних авторов на других версиях MSVC/Clang ломались бы.
- **Выгрузка библиотеки при выключении** — ненадёжна: указатели на код и данные библиотеки могут остаться в
  чужих структурах (§4.6 п. 2).

## Последствия

- Оболочка (1.12) строит меню, этапы, панели и палитру из `registry()` и `command_index()` и пересобирает их
  по событиям менеджера; менеджер модулей (1.14) показывает `plan_enable`/`plan_disable`, `verified()`,
  `incompatibility`, `code_loaded` и работает с профилями.
- Extension host (1.9) реализует `ExtensionRuntime` для `python` и `process` и регистрирует его через
  `set_runtime`; протокол передаёт вызов команды тем же путём, что и C ABI (аргументы и результат — JSON).
- Включение модулей пока не пишется в журнал: журнал воспроизводится тождественно, только если включены те же
  модули (ADR 0004, «Последствия»). Команды `stresslab.extensions.enable/disable` — задача 1.15; там же нужно
  решить, что значит откат транзакции, внутри которой включили модуль.
- Настройки (1.7) проверяют значения по `SettingContribution::schema` и переводят `title`/`description` через
  каталоги `localization`.
- Нативный модуль меняет модель только командами; если модулю понадобятся большие массивы (результаты,
  сетки), C ABI дополнится в новой версии структур без смены `FEM_EXTENSION_ABI_VERSION`.
