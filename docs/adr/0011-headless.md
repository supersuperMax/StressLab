# ADR 0011. Headless-режим: `stresslab --headless run-script`

- Статус: принято
- Дата: 2026-10-13
- Источник: `docs/architecture.md` §4.7, CLAUDE.md правило 9, задача 1.10 из `docs/plan.md`
- Код: `app/` (`app/src/command_line.h`, `headless.h`, `module_pump.h`, `executable_path.h`, `main.cpp`),
  `fem::python::Interpreter::run_script` и `call_soon` (`python/embed/include/fem/python/interpreter.h`),
  ожидание `Task` порциями (`python/bindings/src/tasks.cpp`), `CommandBus::is_idle`,
  `fem::log::Console` (`core/include/fem/core/log/log.h`)

## Контекст

Правило 9: любой сценарий, доступный мышью, должен выполняться без окна — на сервере, в CI, на кластере.
§4.7 называет вход: `stresslab --headless run-script batch.py`. К 1.10 готовы документ с Command Bus и
журналом, настройки и локализация, Extension Manager, extension host внепроцессных модулей (1.9) и встроенный
Python (1.8), но нет программы, которая собирает их вместе без Qt. Открытыми были: какие модули включать без
менеджера модулей, кто вызывает `HostRuntime::poll()`, пока главный поток занят скриптом, какой код возврата,
куда писать лог (бэклог 1.7: два экземпляра делят один файл лога), как сохранить журнал.

## Решения

1. **Командная строка.**

   ```
   stresslab --headless [параметры] run-script <файл.py> [аргументы скрипта]
     --extensions <папка>   поставить модули из подпапок папки (можно несколько раз)
     --profile <файл>       включить модули профиля (ADR 0006), остальные выключить
     --journal <файл.slpy>  писать журнал сессии
     --log-level <уровень>  trace|debug|info|warning|error|critical|off (иначе — настройка log.level)
     --log-file <файл>      писать лог ещё и в файл (дописывая)
   ```

   Параметры стоят до имени скрипта — до или после `run-script`, `--` их заканчивает; всё после имени скрипта
   уходит скрипту, даже если похоже на параметр приложения. Разбор — `fem::app::parse_command_line`, ошибки —
   ключи строк ядра (`app.*`, ru/en) с аргументами. Подкоманда `run-script` оставляет место для будущих
   (`run-journal`, `solve`) без смены синтаксиса.

2. **Коды возврата.** `0` — успех; `n` — `sys.exit(n)` скрипта (`None` → 0, текст → печать и 1); `1` —
   необработанное исключение (traceback в stderr) или сбой приложения (журнал не записан, профиль не читается,
   Python не стартовал); `2` — неверная командная строка: неизвестный параметр, нет `run-script`, нет файла
   скрипта, папки `--extensions` или профиля. Опечатка в пути — ошибка запуска, а не упавший скрипт.

3. **Сборка приложения в headless** (`fem::app::run_headless`): документ, Command Bus, context keys с ключами
   ядра, настройки (пользовательский `settings.json` из `user_folders().config`, если есть; испорченный —
   предупреждение в лог), локализация, связки `fem/core/bindings.h`, Extension Manager с `HostRuntime` для
   `python` и `process` (хост — сам исполняемый файл: `stresslab --python -m stresslab_host`, путь —
   `fem::app::executable_path()`), журнал, встроенный Python, подключённый к документу. Порядок: модули
   ставятся и включаются, затем стартует Python, затем `ExtensionManager::startup()` (модули `onStartup`
   активируются до первой строки скрипта), затем скрипт.

4. **Какие модули включены.** Встроенные (папка `extensions/` дерева исходников, путь зашит при сборке как
   `FEM_PYTHON_SITE_DIR` — поиск рядом с исполняемым файлом в задаче 3.11) и из `--extensions` ставятся; без
   `--profile` включаются все совместимые, с ним — как велит профиль (`apply_profile`), отсутствующие и
   невключаемые модули — ошибки в лог. Сохранённого «набора включённых модулей» пока нет (менеджер модулей —
   1.14); для пакетного запуска явный набор надёжнее неявного состояния пользователя.

5. **Скрипт выполняется как `python файл аргументы`** (`Interpreter::run_script`): `sys.argv = [файл, *арг]`,
   папка скрипта первой в `sys.path`, код — в настоящем `__main__` (pickle и multiprocessing ищут там),
   исходник читается байтами через `io.open_code` и компилируется с именем файла, так что объявление кодировки
   работает, а в traceback нет кадров `runpy`. Не `Py_RunMain`: он сам останавливает Python, а приложению нужно
   до этого обработать оставшиеся запросы модулей, закрыть журнал и выключить модули.

6. **Цикл модулей — отложенные вызовы Python.** Главный поток занят скриптом, а запросы модулей вне их команд
   (фоновые потоки, задачи) ждут `poll()` в потоке модели (ADR 0010 п. 4). `ModulePump` по `on_pending`
   просит `Interpreter::call_soon`, который ставит работу через `Py_AddPendingCall`: Python выполняет её на
   главном потоке между инструкциями байткода — так же, как обработчики сигналов. `poll()` вызывается, только
   если шина свободна (`CommandBus::is_idle`: нет выполняемой команды и открытой транзакции), иначе команда
   модуля стала бы частью шага скрипта; отложенное повторяется по концу шага (`on_journal`). Чтобы скрипт,
   ждущий задачу модуля (`task.result()`), не висел, когда работа задачи сама ждёт `poll`, `Task.wait/result`
   ждут порциями по 50 мс и между ними вызывают `PyErr_CheckSignals()` и `Py_MakePendingCalls()` — заодно
   ожидание прерывается Ctrl+C в обычном Python. После скрипта — `drain()` до пустой очереди.
   Ограничение: блокирующий вызов вне Python (`time.sleep` на минуту, чтение сокета) задерживает запросы
   модулей до своего конца; циклы ожидания со sleep короче секунды работают.

7. **Лог — в stdout, файл — только по просьбе.** Лог headless — часть вывода пакетного запуска, поэтому
   идёт в стандартный вывод вместе с выводом скрипта (stdout Python переводится на построчную буферизацию,
   строки идут в порядке событий), формат — как у файла, без id потока. Файла по умолчанию нет: параллельные
   запуски на сервере не делят один `stresslab.log` (пункт бэклога 1.7 для headless закрыт, для окна —
   остаётся к 1.11). `LogOptions::console` стал перечислением (`none`, `standard_output`, `standard_error`),
   пустая `folder` — без файла. Строки лога — по-английски, как во всём ядре; сообщение о падении модуля
   (`crash_message`) — на языке интерфейса, уровнем warning.

8. **Журнал — `--journal`.** Пишется `FileJournal` по `CommandBus::on_journal` с начала до конца сессии: команды
   скрипта, undo/redo, транзакции и команды модулей «сами по себе». Журнал — снова скрипт: его запуск через
   `run-script` с теми же модулями даёт тот же журнал байт в байт (интеграционный тест).

## Рассмотренные альтернативы

- **`Py_RunMain`** — готовые `sys.argv`, коды и traceback, но Python останавливается внутри, до того как
  приложение закроет журнал и модули; отложенные вызовы после остановки интерпретатора небезопасны.
- **`runpy.run_path`** — проще, но traceback начинается с кадров `<frozen runpy>`, а `__main__` — временный.
- **Отдельный поток для `poll()` с блокировкой модели** — модель однопоточна (ADR 0010, альтернативы).
- **Ручной `stresslab.process_events()` в API** — перекладывает цикл на автора скрипта; забытый вызов вешает
  задачу модуля. Отложенные вызовы работают без участия скрипта.
- **Лог в stderr** (так было задумано в 1.7) — задача требует stdout; stderr остаётся за traceback и
  ошибками командной строки, так их легко отделить.
- **Файл лога с pid в имени** — копил бы файлы в папке пользователя при каждом пакетном запуске; явный
  `--log-file` проще.

## Последствия

- Оболочка (1.11–1.12) делает то же, что `run_headless`, но `poll()` вызывает её цикл событий Qt;
  `ModulePump` — только для режима, где главным потоком владеет Python. Сборку частей приложения
  (`run_headless`) стоит вынести в общий класс, когда появится вторая точка входа.
- `stresslab.Task.wait/result` просыпаются раз в 50 мс; результат задачи приходит без задержки.
- Пути встроенных модулей и Python зашиты при сборке до задачи 3.11.
- Таймауты хоста модулей не вынесены в настройки (бэклог из 1.9 остаётся).
