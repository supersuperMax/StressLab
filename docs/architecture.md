# FEM-APP: архитектура и технологический стек

Версия 0.1, черновик для обсуждения. Интерфейс (внешний вид, UX) разбирается в отдельном трэде «Исследование интерфейсов CAE»; здесь описан только механизм, через который модули добавляют в оболочку свои кнопки, меню и панели.

## 1. Главные решения в двух словах

| Вопрос | Решение |
|---|---|
| Ядро и тяжёлые модули | **C++20** |
| Плагины, скрипты, адаптеры решателей | **Python 3.12** (встроенный интерпретатор) и C++ |
| Графическая оболочка | **Qt 6** (Widgets + Qt Advanced Docking System) |
| 3D-визуализация | **VTK 9** |
| Геометрия | **OpenCASCADE (OCCT)** |
| Сеточные генераторы | **Gmsh** (отдельный процесс), **Netgen** (LGPL) |
| Хранение проекта и результатов | Папка проекта: модель в текстовом виде (JSON) + большие массивы в HDF5-блоках по хэшу |
| Версии и варианты конструкции | Встроенная история в духе git: **libgit2** для модели + своё хранилище больших блоков (раздел 3.1) |
| Система модулей | Манифест + «contribution points» + активация по событиям, по образцу VSCode |
| Внешние решатели | Адаптеры, запускающие решатель отдельным процессом через менеджер заданий |
| Сборка и поставка | CMake + vcpkg, CI на Windows / macOS (arm64 и x64) / Linux |

Почему так: все ключевые открытые библиотеки CAE (OCCT, Gmsh, Netgen, VTK) написаны на C++, а Qt + VTK уже доказали кросс-платформенность на macOS в FreeCAD, ParaView и Salome. Python даёт порог входа для самописных плагинов (оптимизация, динамика) и доступ к numpy/scipy.

## 2. Слои приложения

```

│  Оболочка (Qt 6): окна, доки, дерево модели, 3D-вид, консоль    │
│  рисует только то, что зарегистрировали модули (contributions)  │
├─────────────────────────────────────────────────────────────────┤
│  Ядро платформы (C++)                                           │

│  • Job Manager: запуск и мониторинг внешних процессов            │
│  • Settings, логирование, телеметрия ошибок                      │
├───────────────┬───────────────┬───────────────┬─────────────────┤
│ Нативные      │ Python-       │ Внепроцессные │ Адаптеры        │
│ модули (C++)  │ плагины       │ модули        │ решателей       │
│ геометрия,    │ оптимизация,  │ Gmsh-мешер,   │ CalculiX,       │
│ визуализация, │ постпроцесс,  │ тяжёлые или   │ Abaqus, свой    │
```

Принцип: **ядро ничего не знает о МКЭ-специфике, кроме модели данных**. Mesher, Solver, геометрия, импорт/экспорт форматов и даже сам 3D-вид результатов являются модулями. Встроенные модули поставляются вместе с приложением, но устроены так же, как сторонние, и их тоже можно выключить.

## 3. Модель данных (Model IR)

Единое внутреннее представление, через которое общаются все модули. Ни один модуль не читает чужие форматы напрямую: импортёр переводит файл в IR, экспортёр и адаптер решателя переводят IR в свой формат.

- **Geometry**: B-rep тела OCCT, именованные грани/рёбра (для привязки нагрузок до построения сетки).
- **Mesh**: узлы (float64, SoA-массивы), элементы по типам (C3D10, S4R и т.п. в нейтральной нумерации), наборы узлов/элементов/поверхностей.
- **Model**: материалы, сечения, контакты, шаги анализа, нагрузки, ГУ, запросы вывода.
- **Results**: поля по шагам/инкрементам/модам (узловые, элементные, в точках интегрирования), с единицами измерения.
- **Passthrough**: всё, что импортёр не понял, хранится «сырьём» с привязкой к месту в исходном файле. Это важно для сценария с inp: файл, открытый и сохранённый без изменений, должен совпадать с исходником по смыслу, даже если IR понимает не все ключевые слова Abaqus.

Хранение: в памяти массивы с zero-copy доступом из Python (через buffer protocol / numpy). На диске проект хранится как папка (подробно в 3.1): дерево модели, настройки и список нужных модулей с версиями лежат в JSON, а сетки, геометрия и результаты лежат в HDF5-блоках. HDF5 выбран потому, что на нём уже построены MED, CGNS и формат результатов многих решателей, и он хорошо работает с гигабайтными полями. Для пересылки коллеге проект упаковывается в один файл `.femx` (zip-архив той же папки, с историей или без).

Единицы: модель хранит систему единиц явно; экспортёры обязаны предупреждать при несовпадении (частая причина ошибок при обмене inp ↔ cdb).

## 3.1 Версионирование проекта в духе git

Идея: у проекта есть полноценная история с ветками. Например, на ветке «лонжерон-титан» и ветке «лонжерон-композит» хранятся два варианта крыла; к любой точке можно откатиться, варианты можно сравнить и слить. История отображается графом (как это выглядит, решает трэд по интерфейсу).

### Почему нельзя просто положить HDF5 в git

Если хранить проект одним бинарным файлом `.h5` и коммитить его в обычный git, ничего хорошего не выйдет. Изменение одного материала даёт новый файл на сотни мегабайт, git не умеет считать дельты для HDF5, а сравнение и слияние невозможны: репозиторий раздувается за несколько десятков коммитов. Поэтому формат хранения проектируется сразу под историю.

### Как устроено хранение

```
wing.femproj/
├── project.json          # версия формата, нужные модули, система единиц
├── model/                # ОПИСАНИЕ МОДЕЛИ: текст, по файлу на объект
│   ├── materials/al-2024.json
│   ├── sections/skin-upper.json
│   ├── steps/cruise-load.json
│   ├── loads/…  bcs/…  sets/…
│   └── ext/fem.dynamics/…       # объекты модулей, по owner
├── refs/blobs.json       # ссылки на большие блоки: {"mesh/main": "sha256:…"}
└── .fem/                 # служебное, как .git
    ├── git/              # история модели (libgit2)
    ├── objects/sha256/…  # хранилище блоков (content-addressed, zstd)
    └── cache/results/…   # кэш результатов (см. ниже)
```

Три вида данных хранятся по-разному:

| Данные | Пример | Как версионируются |
|---|---|---|
| **Описание модели** | Материалы, сечения, шаги, нагрузки, ГУ, параметры сетки и решателя, ссылки на геометрию | Текстовый JSON с детерминированной сериализацией (сортированные ключи, фиксированный формат чисел), по файлу на объект. Хранится в git через **libgit2**: дешёвые коммиты, нормальные диффы, трёхстороннее слияние |
| **Большие входные блоки** | Сетка, B-rep геометрия, импортированные таблицы | Неизменяемые HDF5-блоки в хранилище по хэшу содержимого (как git-lfs / DVC). Модель ссылается на блок хэшем. Одинаковый блок в десяти коммитах хранится один раз; большие сетки режутся на куски, чтобы локальное изменение не дублировало всю сетку |
| **Результаты расчётов** | Поля напряжений, перемещений, формы колебаний | **По умолчанию не входят в историю.** Хранятся в кэше с ключом `хэш(модель + сетка + решатель и его версия)`, каждый результат помечен коммитом, из которого посчитан. Если результат удалён, его можно пересчитать. Важный результат можно «закрепить» (pin), тогда он входит в историю и в архив для коллег |

Такое разделение держит историю маленькой: коммит «толщина обшивки 2 → 3 мм» весит несколько сотен байт, а не гигабайт.

### Что видит пользователь

- **Коммит = осознанная контрольная точка** с подписью («Вариант с 5 нервюрами»). Undo/redo остаётся отдельным быстрым механизмом внутри сессии; история не засоряется каждым кликом. Дополнительно приложение делает автоснимок перед рискованными операциями (перестроение сетки, импорт, слияние) и перед каждым запуском расчёта, поэтому любой результат всегда привязан к точной версии модели.
- **Ветки = варианты конструкции.** Создать вариант, переключиться, вернуться. Переключение ветки подменяет модель в окне; несохранённые изменения предлагается зафиксировать или отложить (аналог `git stash`).
- **Откат:** вернуть весь проект к точке истории или только один объект («верни материал лонжерона как было три коммита назад»).
- **Сравнение вариантов.** Дифф показывается в терминах модели, а не файлов: «Сечение skin-upper: толщина 2 → 3 мм; добавлена нагрузка gust-2; сетка перестроена (48 312 → 61 007 элементов)». Работает и для объектов модулей, потому что их поля описаны в `propertySchemas` (4.2). Результаты двух веток можно открыть рядом или посчитать разность полей, если сетки совпадают; если нет, разность считается после интерполяции на общую сетку (это делает модуль постобработки).
- **Слияние вариантов.** Объекты модели сливаются по полям трёхсторонним слиянием. Конфликт (оба варианта поменяли толщину по-разному) показывается в интерфейсе с выбором значения. Сетки и геометрия не сливаются: при конфликте берётся одна сторона или сетка перестраивается по слитым параметрам.
- **Связь с журналом:** у каждого коммита есть Python-журнал действий от предыдущего коммита. Это делает историю понятной («что именно я поменял») и позволяет повторить те же шаги на другой ветке.

### Совместная работа

Внутри это настоящий git-репозиторий, поэтому позже проект можно синхронизировать с GitHub/GitLab или своим сервером: модель идёт обычными git-объектами, а блоки и закреплённые результаты отдельным протоколом хранилища (как git-lfs). Для MVP достаточно локальной истории и экспорта в `.femx`.

### Технология

- **libgit2** (C, GPLv2 с linking exception, поэтому её можно линковать в приложение при любой лицензии) для коммитов, веток, слияния текстовой части.
- Хранилище блоков: своё, простое, на C++: SHA-256, zstd, HDF5 внутри блока, сборка мусора неиспользуемых блоков по команде «Очистить проект».
- Модуль `fem.history` в ядре: API `commit / branch / checkout / diff / merge / log` доступен из Python и записывается в журнал, как любые команды.

### Риски

- Детерминированная сериализация обязательна, иначе диффы будут показывать «изменения», которых нет. Это требование ко всем модулям, оно проверяется тестами (сохранить → загрузить → сохранить даёт идентичные байты).
- Объекты модуля, который выключен или удалён, всё равно хранятся и показываются в диффе как сырой JSON.
- Кэш результатов может вырасти до сотен гигабайт; нужны лимит размера и понятная очистка («удалить результаты неактивных веток»).

## 4. Система модулей в стиле VSCode

### 4.1 Что такое модуль

Папка с манифестом `fem-extension.toml` и кодом (C++ библиотека, Python-пакет или исполняемый файл).

```toml
[extension]
id = "fem.calculix"
name = "CalculiX Solver"
version = "1.2.0"
engine = "^1.0"                 # совместимая версия API платформы
kind = "python"                 # native | python | process
entry = "calculix_adapter:activate"
requires = ["fem.format.abaqus-inp>=1.0"]

# Когда загружать. Модуль не грузится, пока событие не произошло.
activation = ["onSolverRequested:calculix", "onCommand:calculix.*", "onOpenFile:*.frd"]

[[contributes.solvers]]
id = "calculix"
label = "CalculiX"
analyses = ["static", "frequency", "buckling", "heat", "dynamic"]

[[contributes.commands]]
id = "calculix.run"
title = "Запустить CalculiX"
icon = "icons/run.svg"

[[contributes.menus]]
location = "solve/run"
command = "calculix.run"
when = "model.hasMesh && solver.calculix.available"

[[contributes.contextToolbar]]
command = "calculix.run"
when = "stage == 'solve'"

[[contributes.bottomPanelTabs]]
id = "calculix.monitor"
title = "Монитор CalculiX"
when = "job.running && job.solver == 'calculix'"

[[contributes.fileFormats]]
id = "calculix-frd"
extensions = [".frd"]
role = "results-import"

[contributes.settings]
"calculix.executable" = { type = "path", default = "", description = "Путь к ccx (пусто = искать в PATH)" }
"calculix.threads"    = { type = "integer", default = 0, description = "0 = по числу ядер" }
```

### 4.2 Точки расширения (contribution points)

Список согласован с разделом 6 документа по интерфейсу ([interface-design.md](/mnt/project-files/ui/interface-design.md#6-как-модули-проявляются-в-интерфейсе)). Модуль **встраивается, а не рисует**: он заполняет только эти места стандартными элементами оболочки и не может открывать собственные окна, менять чужие панели или показывать модальные окна при старте.

| Точка | Что добавляет модуль | Ограничения |
|---|---|---|
| `commands` | Действия с id; вызываются из меню, палитры команд, контекстной панели, Python | Каждая команда обязана иметь Python-сигнатуру (см. 4.7) |
| `stages` | Этап или подэтап на полосе этапов | Только в заданные слоты: `before:<этап>` / `after:<этап>`; переставлять стандартные этапы нельзя |
| `treeNodeTypes` | Типы узлов дерева модели и их контекстное меню | Узел принадлежит модулю (`owner`), см. 4.7 |
| `contextToolbar`, `menus`, `contextMenus` | Места, где команда видна, с условием `when` | — |
| `propertySchemas` | Формы свойств для своих узлов: поля, типы, единицы, допустимые значения | Только декларативно (JSON Schema + расширения для единиц); оболочка рисует форму сама |
| `fileFormats` | Открытие/импорт/экспорт моделей, сеток, результатов | Должен сообщать, что теряется при конвертации |
| `solvers` | Адаптер решателя (см. раздел 6) | Обязателен `detect()` и `validate()` |
| `meshers` | Генератор сетки с параметрами через `propertySchemas` | — |
| `activityBar` | Иконка с собственной боковой панелью | Не больше одной на модуль |
| `bottomPanelTabs` | Вкладка нижней панели (лог решателя, графики) | — |
| `viewportLayers` | Слои отображения и инструменты постобработки в 3D-виде | — |
| `resultFilters` | Операции постпроцессинга (запас прочности, усталость, сечения) | — |
| `settings` | Раздел настроек по схеме | Оболочка строит форму сама |
| `keybindings`, `icons`, `localization` | Горячие клавиши, иконки, переводы (ru/en с первого дня) | — |

### 4.3 Как кнопки появляются и исчезают

Оболочка не содержит «зашитых» МКЭ-кнопок. Она хранит реестр contributions и пересобирает меню/тулбары при двух событиях:

1. **Модуль включён или выключен**: его contributions добавляются в реестр или удаляются, и UI обновляется сразу, без перезапуска.
2. **Изменился контекст**: ядро поддерживает словарь context keys (`model.hasMesh`, `selection.type == 'face'`, `stage`, `tree.selectedNodeType`, `solver.abaqus.available`, `job.running`…). Модули могут объявлять свои ключи. Условия `when` вычисляются заново при изменении ключей, поэтому команда «Запустить Abaqus» не видна, если Abaqus не найден, а меню «Оптимизация» появляется только при включённом модуле оптимизации.

Как это выглядит и где лежит, решает трэд по интерфейсу; этот механизм даёт ему инструмент.

### 4.4 Три вида модулей и изоляция

| Вид | Где работает | Для чего | Цена |
|---|---|---|---|
| `native` (C++) | В процессе приложения, через стабильный C ABI | Геометрия, рендер, быстрые форматы | Падение модуля роняет приложение; нужна сборка под каждую ОС |
| `python` | В отдельном **extension host** процессе (как в VSCode); опционально в главном для быстрых UI-скриптов | Плагины пользователей, адаптеры решателей, оптимизация, автоматизация | Медленнее C++, но zero-copy через shared memory |
| `process` | Отдельный исполняемый файл | Gmsh и другие GPL-компоненты, долгие вычисления, свой решатель | Обмен через IPC и файлы |

Обмен с внепроцессными модулями: **JSON-RPC поверх stdio/сокета** (как Language Server Protocol) для команд и событий, **shared memory или HDF5-файлы** для больших массивов. Если плагин зависает или падает, extension host перезапускается, а приложение и несохранённая модель остаются целы.

### 4.5 Менеджер модулей внутри приложения

- Список установленных модулей: включить, выключить, обновить, удалить, открыть настройки.
- Каталог (marketplace): на старте JSON-реестр в Git-репозитории + архивы `.femext` (zip с манифестом и подписью); позже свой сервер.
- Проверка зависимостей и версии `engine` перед включением.
- Профили: набор включённых модулей и раскладка окна под задачу («Прочность», «Тепло», «Оптимизация»), переключаются в один клик и передаются коллеге файлом.
- Модули на Python ставят свои зависимости в собственную папку `site-packages` модуля, чтобы не конфликтовать друг с другом (по образцу Blender).
- Безопасность: модуль из каталога подписан; модуль из локальной папки помечается как «непроверенный» с предупреждением при включении.

### 4.6 Требования интерфейса к механизму модулей

Ниже ответ на раздел 13 [interface-design.md](/mnt/project-files/ui/interface-design.md#13-что-интерфейсу-нужно-от-механизма-расширений). Расхождений по сути нет; есть одна оговорка про нативные модули (пункт 2).

1. **Декларативный манифест.** Да: всё, что модуль показывает, описано в `fem-extension.toml`. Оболочка строит меню, этапы, формы и пункты палитры по манифесту, не загружая код; код грузится по событию активации.
2. **Включение/выключение без перезапуска.** Да: Extension Manager шлёт событие `extension.deactivated(id)`, оболочка убирает все contributions с этим `owner`, команды снимаются с регистрации, extension host выгружает Python-модуль. **Оговорка:** C++-модуль из интерфейса исчезает сразу, но его библиотека физически выгружается из памяти только при следующем запуске (выгрузка нативного кода из работающего процесса ненадёжна). Пользователь этого не замечает.
3. **Формы по схеме.** Да, `propertySchemas` (4.2). Схема та же, что и для `settings`, один генератор форм на всё.
4. **Узлы отключённых модулей сохраняются.** Да: каждый объект Model IR хранит `owner` (id модуля) и версию схемы. Когда модуль выключен, его объекты остаются в модели как «непрозрачные» блоки (данные + схема), скрываются из дерева, сохраняются в `.femx` без изменений и возвращаются при включении. Файл проекта перечисляет нужные модули с версиями, отсюда полоса «Модели нужны модули… [Включить] [Открыть без них]». Ядро запрещает удалять объект, от которого зависит объект выключенного модуля, и показывает почему.
5. **Каждая команда доступна из Python, вызовы пишутся в журнал.** Да: Command Bus единственный путь изменить модель. Каждый вызов команды сериализуется в строку Python (`femapp.cmd("calculix.run", job="bracket")` или типизированная обёртка `femapp.calculix.run(job="bracket")`), пишется в журнал сессии `.fempy` и в стек undo. Отсюда «Сохранить журнал как скрипт» и запуск `femapp --headless`.
6. **Доступность решателей и форматов.** Да: `detect()`, `check_license()`, `validate()` у решателей (раздел 6); форматы реализуют `describe_losses(model)` перед экспортом. Результаты попадают в context keys и в карточку модуля.
7. **Асинхронные долгие операции с прогрессом и отменой.** Да: любая команда может вернуть `Task` (прогресс, сообщения, отмена). Задания решателя идут через Job Manager, импорт и построение сетки через тот же механизм задач; оболочка показывает их во вкладке «Задания» и не блокируется.
8. **Поиск команд выключенных модулей.** Да: манифесты установленных, но выключенных модулей остаются в индексе палитры команд с пометкой «выключен», выбор предлагает включить модуль. Индекс каталога (не установленных модулей) можно подключить к поиску позже.
9. **Полоса этапов.** Принимаю предложение интерфейса: модули только добавляют этапы в слоты `before:`/`after:` стандартных этапов.
10. **Профили.** Профиль = файл со списком модулей, их версий и раскладкой окна; формат JSON, переносится между машинами.

### 4.7 Публичный API

Одно API на C++ с автоматически сгенерированными Python-привязками (**nanobind**, запасной вариант pybind11). Тот же API доступен из встроенной Python-консоли и для запуска без GUI:

```bash
femapp --headless run-script batch.py     # пакетный расчёт без окна
```

Это закрывает автоматизацию и запуск на серверах/кластерах.

## 6. Адаптер решателя

Каждый решатель реализует один интерфейс:

```python
class SolverAdapter:
    def detect(self) -> SolverInstall | None: ...           # найден ли, версия, путь
    def check_license(self, inst) -> LicenseStatus: ...     # доступна ли лицензия (без запуска расчёта)
    def validate(self, model) -> list[Issue]: ...           # что из модели решатель не поддерживает
    def write_input(self, model, workdir) -> JobSpec: ...   # IR → входной файл
    def run(self, job, ctx: JobContext) -> None: ...        # запуск через Job Manager
    def parse_progress(self, line_or_file) -> Progress: ... # инкременты, сходимость
    def read_results(self, job) -> Results: ...             # выходные файлы → Results IR
```

**Job Manager** (часть ядра) запускает процессы, показывает прогресс, умеет отменять задание, держит очередь. Архитектура заложена так, чтобы потом добавить удалённый запуск (SSH, Slurm/PBS) без изменения адаптеров: адаптер описывает команду и файлы, а где её выполнить, решает Job Manager.

`detect()` вызывается при старте и в настройках; результат пишется в context keys (`solver.abaqus.available`), отсюда исчезающие кнопки из 4.3.

## 7. Сценарий из запроса: inp → CalculiX/Abaqus → результат для Ansys

```
 .inp ──► [abaqus-inp импортёр] ──► Model IR ──► дерево модели, 3D-вид
                                         │
              пользователь выбирает решатель из найденных
                 ┌───────────────────────┴───────────────────────┐
          [calculix адаптер]                              [abaqus адаптер]
   validate: что не поддерживает ccx              detect + check_license
   write_input: inp в диалекте ccx                write_input: исходный inp
   Job Manager: ccx -i job                       Job Manager: abaqus job=… interactive
   read_results: .frd/.dat ─┐                     read_results: .odb ─┐
                            ▼                                         ▼
                       Results IR ◄──────────────────────────── дамп в HDF5
                            │                                  (через abaqus python)
                 просмотр в fem.results.viewer
                            │
                  [fem.export.ansys] ──► файлы, которые открывает Ansys
```

### 7.1 CalculiX

- CalculiX понимает только подмножество ключевых слов Abaqus. Поэтому `validate()` до запуска показывает список неподдерживаемых карт (например, часть типов элементов, некоторые опции контакта и вывода) и предлагает замену или отказ, а не падает в середине расчёта.
- Результаты: `.frd` (поля) и `.dat` (табличный вывод) читаются собственным парсером.
- CalculiX под GPL, но запускается как внешняя программа, поэтому на лицензию нашего приложения не влияет. Бинарники ccx можно поставлять вместе с приложением для всех трёх ОС, чтобы «из коробки» был хотя бы один решатель.

### 7.2 Abaqus

- `detect()`: поиск команды `abaqus` в PATH и типовых путях установки; версия через `abaqus information=release`.
- Лицензия: проверка доступности до запуска (точный способ проверки уточнить на реальной установке; на старте достаточно запустить расчёт и разобрать ошибку лицензии из лога понятным сообщением).
- **Важное ограничение:** формат `.odb` закрытый, читать его можно только через Python API самого Abaqus. Адаптер поставляет маленький скрипт, который выполняется командой `abaqus python dump_odb.py job.odb out.h5` и выгружает поля в наш HDF5. Значит, для чтения результатов Abaqus у пользователя должен быть установлен Abaqus (что в этом сценарии и так выполнено). Abaqus официально не работает на macOS, поэтому там этот адаптер будет доступен только для удалённого запуска.

### 7.3 Экспорт результата, понятного Ansys

Честная картина: открытого формата, который Ansys Mechanical откроет как «свои» результаты, нет. Варианты, от простого к сложному:

| Вариант | Где коллега смотрит | Сложность | Комментарий |
|---|---|---|---|
| **EnSight Gold** (`.case`) | Ansys EnSight (входит в линейку Ansys) | Низкая | Открытый документированный формат, поля по шагам; рекомендую как первый вариант |
| **CGNS** | Ansys CFD-Post / EnSight | Средняя | Хорош для тепла и CFD-подобных данных |
| **cdb + External Data** | Ansys Mechanical | Средняя | Сетка через cdb, поля как CSV/таблицы в External Data Import; удобно для передачи нагрузок/температур, не для полноценного постпроцессинга |
| **Нативный `.rst` (MAPDL)** | Ansys Mechanical APDL, Mechanical | Высокая | Формат описан в документации Ansys (Programmer's Reference), библиотеки для чтения существуют (pyansys), но запись придётся делать и проверять самим на реальной установке Ansys. Это исследовательская задача, а не MVP |

План: в MVP EnSight Gold + VTK (для ParaView), затем cdb + External Data, `.rst` отдельным исследовательским модулем. Оценка применимости EnSight и `.rst` выше сделана по моим знаниям форматов и требует проверки на установленном Ansys.

## 8. Кросс-платформенность

- **Qt 6** даёт нативные окна, меню (включая верхнюю строку меню macOS), HiDPI/Retina, тёмную тему.
- **Рендеринг:** VTK сейчас работает через OpenGL. На macOS OpenGL объявлен устаревшим, но продолжает работать (в том числе на Apple Silicon). Риск закрывается так: весь рендер изолирован в модуле `fem.results.viewer`/`fem.viewport`, а у VTK в разработке бэкенд WebGPU (Metal/Vulkan/D3D12), на который можно будет перейти без переделки остального приложения.
- **Линейная алгебра для своего решателя** (позже): не завязываться на Intel MKL/PARDISO (на Apple Silicon нет). Использовать Eigen + MUMPS/PETSc, на macOS при желании Apple Accelerate.
- **Пути, процессы, кодировки:** только через Qt/`std::filesystem`, UTF-8 везде; отдельно протестировать пути с кириллицей и пробелами на Windows (типичная беда CAE-софта).
- **CI:** GitHub Actions, сборка и тесты на Windows x64, macOS arm64 и x64, Ubuntu; эталонные модели (inp + ожидаемые результаты) прогоняются на всех трёх.
- **Поставка:** Windows MSI/MSIX, macOS подписанный и нотаризованный `.dmg` (Universal 2), Linux AppImage и Flatpak. Python и ccx встроены в дистрибутив.

### Рассмотренные и отвергнутые альтернативы

- **Rust для ядра.** Безопаснее, но OCCT, Gmsh, VTK, Qt придётся подключать через FFI-обёртки, которых в зрелом виде нет. Можно вернуться к Rust для отдельных модулей (например, парсеров) благодаря C ABI.
- **Electron/Tauri + веб-визуализация (vtk.js, trame).** Проще сделать красивый интерфейс, но сетки на миллионы элементов и большие поля результатов в браузерном рендере работают заметно хуже, а связка с OCCT/Gmsh всё равно потребует нативного бэкенда. Веб-клиент имеет смысл позже как просмотрщик результатов для коллег.
- **Весь продукт на Python (как ранние прототипы).** Быстро стартовать, но GUI с большой 3D-сценой и GIL упрутся в производительность.
- **Целиком строить на FreeCAD/Salome.** Готовые наработки, но их архитектура модулей (workbench) не даёт динамического включения/выключения и условной видимости UI так, как мы хотим, а кодовая база огромная. Брать у них можно идеи и отдельные библиотеки.

## 10. Лицензирование: открытое ядро + платные модули

Решение: ядро и бесплатные модули открытые, платные модули (оптимизация, динамика и т.п.) появятся позже (модель open core, как у VSCode с платными расширениями или у GitLab).

### Почему MIT, а не GPL

Из двух вариантов для ядра выбрана **MIT** (рассматривалась и Apache-2.0: она тоже разрешительная и даёт явную патентную защиту; её можно выбрать вместо MIT без изменений в архитектуре). Причина в том, что GPL мешает платным модулям:

- Модуль на C++ или Python, который загружается в процесс приложения и вызывает его API, по позиции FSF считается производной работой от GPL-ядра. Значит, его тоже пришлось бы открыть под GPL, и продавать закрытый модуль было бы нельзя.
- Обойти это можно двумя способами: добавить к GPL «исключение для плагинов» или держать платные модули только в отдельных процессах. Первое создаёт юридическую неопределённость для сторонних авторов, второе лишает платные модули быстрого доступа к модели в памяти.
- С MIT таких проблем нет: платный модуль может быть закрытым и работать в процессе, как любой другой.

Минус MIT в том, что кто-то может взять ядро и сделать закрытый форк. Для open core это обычный и приемлемый риск: ценность в платных модулях и в сообществе.

### Как с этим сочетаются зависимости

| Зависимость | Лицензия | Что из этого следует при MIT-ядре |
|---|---|---|
| Qt 6, OCCT, Netgen | LGPL | Линкуются динамически, пользователь может заменить библиотеку; при соблюдении этого ядро остаётся MIT |
| VTK, HDF5, Eigen, nanobind, zstd | BSD / MPL2 и подобные | Без ограничений |
| libgit2 | GPLv2 с linking exception | Исключение разрешает линковать в приложение под любой лицензией |
| Gmsh | GPL | Работает отдельным процессом через небольшую программу-посредник; посредник открыт под GPL, ядро остаётся MIT |
| CalculiX (ccx) | GPL | Отдельная программа; поставляется в дистрибутиве вместе с исходниками или ссылкой на них |
| TetGen | AGPL | Не используется |

### Что нужно в архитектуре для платных модулей (позже)

- **Проверка лицензии модуля** через отдельный сервис ядра `fem.licensing`: ключ или учётная запись, офлайн-активация на N дней, привязка к пользователю, а не к железу (кросс-платформенность и ноутбуки). Модуль сам решает, какие функции закрыть; ядро только отвечает «лицензия есть / нет / истекла».
- **Каталог** различает бесплатные и платные модули, показывает пробный период.
- **Подпись пакетов** (раздел 4.5) обязательна для платных модулей.
- **Объекты платного модуля в модели** хранятся открыто, как у любого модуля (раздел 4.6): если лицензия истекла, модель открывается и сохраняется без потерь, просто эти узлы недоступны для редактирования и расчёта. Пользователь не должен терять свои данные из-за лицензии.

Перед первым платным модулем нужна проверка лицензий юристом.

## 11. Порядок разработки

1. **Каркас (MVP-0):** ядро, Command Bus с журналом на Python и undo, context keys, Extension Manager с вкл/выкл без перезапуска, оболочка Qt с пустыми зонами, Python extension host, CI на трёх ОС. Критерий готовности: демонстрационный модуль добавляет кнопку, которая исчезает при выключении модуля.
2. **История проекта (входит в MVP-0/1):** формат папки проекта, коммиты, ветки, откат, дифф модели. Слияние и синхронизация с сервером позже.
3. **Сценарий из запроса (MVP-1), только линейная статика:** импорт inp → просмотр сетки → CalculiX (встроенный ccx) → просмотр результатов → экспорт EnSight Gold/VTK. Model IR в MVP-1 покрывает: узлы, элементы (C3D4/C3D10, C3D8/C3D20, S3/S4, B31), наборы, упругий изотропный материал, сечения, один или несколько шагов `*STATIC`, закрепления, сосредоточенные и распределённые нагрузки, давление, гравитацию; результаты: перемещения, напряжения, деформации, реакции. Нелинейность, контакт, частоты и тепло добавляются после MVP-1; всё прочее из inp сохраняется через passthrough.
4. **Abaqus и Ansys-обмен:** адаптер Abaqus с выгрузкой odb, импорт/экспорт cdb, External Data.
5. **Препроцессинг:** геометрия OCCT, Gmsh/Netgen, задание нагрузок на геометрию.
6. **Каталог модулей и SDK:** шаблон модуля, документация API, подпись пакетов.
7. **Свои фишки:** оптимизация, динамика, свой решатель, исследование записи `.rst`.
8. **Облако:** удалённый и облачный запуск расчётов через Job Manager, синхронизация проектов и истории через сервер.

- ~~Нужен ли многопользовательский/облачный режим?~~ Решено: облако планируется, но первые версии работают локально (сначала сосредоточиться на текущей архитектуре). Чтобы облако потом не потребовало переделки, уже сейчас соблюдаются три правила: Job Manager отделяет «что запустить» от «где запустить» (раздел 6), проект хранится как git-репозиторий с блоками по хэшу (раздел 3.1), а всё доступно через API без GUI (`--headless`, раздел 4.7). Облачный запуск расчётов и синхронизация проектов добавляются отдельным этапом после MVP.
- ~~Какие типы анализов приоритетны для первого релиза?~~ Решено: в первом релизе линейная статика (см. раздел 11, пункт 3).
